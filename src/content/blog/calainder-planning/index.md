> **Calainder** = **Cal**endar + **AI** + Remi**nder**. 텍스트와 이미지 속 일정 정보를 AI가 분석해 Google Calendar에 자동으로 등록하는 서비스입니다. 이 글은 구현에 들어가기 전, 무엇을 만들지 정한 기획 과정을 정리합니다. 구현과 트러블슈팅은 [프로젝트 페이지](/projects/calainder)에 있습니다.

## 1. 문제 정의

기존 캘린더는 사용자가 일정을 직접 입력해야 해서 기록이 번거롭고, 꾸준히 쓰기 어려웠습니다. 게다가 일정 정보는 메신저, 공지사항, 대화 내용, 이미지 캡처처럼 여러 곳에 흩어져 있어, 이를 다시 정리해 캘린더에 옮겨 적는 일이 반복됩니다.

> **핵심 문제:** 사용자는 흩어진 일정 정보를 관리해야 하지만, 이를 직접 정리하고 캘린더에 입력하는 과정이 번거롭고 반복적이다.
>
> **해결 방향:** 텍스트·이미지처럼 비정형으로 흩어진 일정 정보를 AI가 분석하고, 사용자가 이미 쓰는 Google Calendar에 자동으로 반영한다.

## 2. 핵심 요구사항

1. 텍스트, 대화 내용, 이미지 같은 **비정형 입력만으로** 일정을 등록할 수 있어야 한다.
2. 입력에서 제목, 날짜, 시간을 **자동으로 추출**해야 한다.
3. 추출한 일정은 **Google Calendar에 자동 등록·동기화**되어야 한다.
4. 등록된 일정은 Google Calendar에서 확인하고, 필요하면 수정·삭제할 수 있어야 한다.
5. **E-Class** 같은 외부 서비스의 과제 일정도 수집해 반영할 수 있어야 한다.
6. 등록한 일정의 **알림**까지 확장할 수 있어야 한다.

## 3. 유스케이스: 누가 무엇을 하는가

![Calainder 유스케이스 다이어그램](/images/blog/calainder-planning/usecase.webp)

액터는 **학생/직장인**, **Google Calendar**, **E-Class** 셋으로 잡았습니다.

| 유스케이스 | 내용 |
| --- | --- |
| UC-01 일정 업로드 및 등록 | 텍스트나 이미지를 올리면 분석해 일정을 등록하고 Google Calendar와 동기화 |
| UC-02 일정 관리 | 등록된 일정을 확인하고 수정·삭제 |
| UC-03 과제 일정 업데이트 | E-Class에서 과제 일정을 수집해 캘린더에 반영 |
| UC-04 알림 기능 (확장) | 등록된 일정의 알림을 확인하고 리마인더로 확장 |

이렇게 나누고 보니 Calainder는 단순한 일정 등록이 아니라 **AI 분석, 캘린더 연동, 외부 일정 수집, 알림 확장**까지 이어지는 서비스라는 범위가 분명해졌습니다.

## 4. 시퀀스: 입력이 어떤 순서로 처리되는가

![Calainder 시퀀스 다이어그램](/images/blog/calainder-planning/sequence.webp)

사용자 입력이 서버 안에서 어떤 순서로 흘러가는지 두 가지 흐름과 예외로 정리했습니다.

**일정 자동 등록**
1. 사용자가 이미지나 대화 내용을 올린다.
2. 웹 화면이 데이터를 Spring Boot 서버로 보낸다.
3. 서버가 AI 분석 모듈에 프롬프트와 입력을 보내 분석을 요청한다.
4. AI 모듈이 제목·날짜·시간을 돌려준다.
5. 서버가 Google Calendar API에 일정 등록을 요청한다.
6. 등록되면 화면에 "일정 자동 등록 완료"를 띄운다.

**학교 과제 일정 업데이트**
1. 사용자가 과제 일정 업데이트를 요청한다.
2. 서버가 E-Class 크롤러에 로그인과 과제 수집을 요청한다.
3. 크롤러가 돌려준 과제 일정을 서버가 Google Calendar에 등록·동기화한다.

**예외** — AI 분석에 실패하면 분석 불가 메시지를, Google Calendar 동기화에 실패하면 API 오류 메시지를 돌려주고, 화면은 오류를 보여 주며 재시도를 안내합니다.

결국 모든 흐름이 **사용자 입력 → 서버 → AI 분석 또는 크롤링 → Google Calendar 반영 → 결과 반환** 하나의 구조로 모인다는 걸 확인할 수 있었습니다.

## 5. 화면 설계: 자체 캘린더에서 채팅형 입력으로

처음에는 웹사이트 안에 **직접 달력 화면**을 만들고, Google Calendar 데이터를 불러와 자체 캘린더에서 일정을 관리하려 했습니다.

기획을 구체화하면서 생각이 바뀌었습니다. 사용자가 일정을 하나하나 관리하는 화면보다, **텍스트와 이미지로 AI에게 자연스럽게 일정을 요청하는 흐름**이 Calainder가 해결하려는 문제("입력이 번거롭다")에 더 가까웠기 때문입니다.

> **기획 전환:** 자체 캘린더 중심 UI → **채팅형 입력 중심 UI**

- 메인 화면은 GPT 프롬프트 입력창과 비슷한 **채팅형 인터페이스**로 설계했다.
- AI가 분석한 일정은 **카드**로 보여 주고, Google Calendar에 등록됐음을 확인할 수 있게 했다.
- 실제 일정 확인과 관리는 버튼으로 **Google Calendar로 이동**해서 하게 했다. 이미 익숙한 도구를 다시 만들지 않았다.
- E-Class 과제 수집도 같은 채팅 흐름 안에서 요청하게 했다.
- 등록 직후 결과 카드에서 바로 **수정**할 수 있게 했다.

이 전환으로 Calainder는 **"일정 입력의 번거로움을 줄이는 일"에만 집중**하고, 확인과 관리는 Google Calendar에 맡기는 구조가 됐습니다.

## 6. 기획에서 정한 설계 결정

화면 방향이 정해지자 서버 구조도 같은 원칙으로 정리됐습니다.

| 결정 | 이유 |
| --- | --- |
| **일정의 최종 저장소는 내부 DB가 아니라 Google Calendar** | 입력 → 분석 → 반영이라는 핵심 흐름에 집중하고, 사용자가 실제로 쓰는 캘린더에 바로 연결하기 위해 |
| **Controller-Service-DTO/Util 구조** | 자체 DB가 없으니 Repository 계층까지 두지 않고, 요청 처리·비즈니스 로직·데이터 변환만 나눠 단순화 |
| **E-Class 로그인 정보는 AES로 암호화해 크롤러에 전달** | 외부 모듈과 주고받는 과정에서 민감정보가 평문으로 오가지 않게 |
| **리마인더는 Google Calendar 알림 옵션과 연결** | 별도 알림 저장소 없이, 등록 직후 스위치로 알림 여부와 시간(분 단위)을 고르게 |
| **AI·크롤링 호출은 비동기·큐 구조로 확장 가능하게** | 외부 호출은 오래 걸릴 수 있어 연쇄 호출의 응답 지연을 고려 |

내부 DB를 두지 않은 결정에는 한계도 있습니다. 일정 히스토리, 분석 로그, 서비스 안의 독립 일정 저장 같은 기능이 필요해지면 별도 데이터 구조로 확장해야 한다는 점을 기획 단계에서 함께 적어 두었습니다.

## 배운 점

- 기획 산출물(요구사항 → 유스케이스 → 시퀀스)을 순서대로 만들면, 서비스의 **범위와 경계**가 그림으로 보인다.
- 화면 설계는 기능 목록이 아니라 **해결하려는 문제**에 맞춰야 한다. "입력이 번거롭다"는 문제에는 달력 화면보다 채팅 입력이 맞았다.
- 이미 익숙한 도구(Google Calendar)가 잘하는 일은 다시 만들지 않고 **연결**하는 게 범위를 줄이는 가장 좋은 방법이었다.
