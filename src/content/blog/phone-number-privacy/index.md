## 상황

Korea Score Predictor는 참여자에게 휴대폰 번호를 받습니다. 이 번호에는 성격이 다른 세 가지 요구가 걸려 있었습니다.

| 요구 | 필요한 것 |
| --- | --- |
| 같은 사람의 중복 참여 판단 | 번호끼리 **같은지 비교**할 수 있어야 함 |
| 당첨자에게 연락 | **원본 번호**가 필요함 |
| 관리자 화면·결과 화면 | 번호가 **최소한으로만** 보여야 함 |

원본 번호를 그대로 저장하면 세 가지를 모두 쉽게 해결할 수 있지만, 관리자 화면에 항상 원본이 보이는 구조는 개인정보 측면에서 부담이 컸습니다.

## 설계

요구마다 다른 방식을 적용했습니다.

1. **비교용 — HMAC SHA-256 해시**
   번호를 정규화한 뒤 서버 secret으로 HMAC SHA-256 해시를 만들어 `phone_hash`로 저장합니다. 중복 참여 판단은 이 값으로만 합니다.
2. **표시용 — 마지막 4자리 마스킹**
   관리자 화면에는 `010-****-1234` 형태로만 보여줍니다.
3. **연락용 — AES-256-GCM 선택적 암호화**
   당첨자 연락에 원본이 필요할 때를 위해 번호를 암호화해 저장하고, **당첨자 CSV export에서만** 복호화합니다. 과거 데이터처럼 복호화할 수 없는 경우에는 마스킹 번호만 제공합니다.

CSV에는 실제 경기 결과와 정확히 일치한 당첨자만, 필요한 최소 필드만 담았습니다.

## 키 관리

- 해시 secret, 암호화 key, Supabase service role key는 **서버 환경 변수로만** 사용
- 민감한 로직은 클라이언트 컴포넌트가 아니라 Next.js Server Action과 server-only helper에서 처리해, 브라우저로 키가 전달되지 않도록 함

## 배운 점

- "번호를 저장한다"는 하나의 기능도 **비교·표시·연락**으로 쪼개 보면 각각 다른 보호 수준을 적용할 수 있다.
- 해시는 비교만, 암호화는 복원이 필요할 때만. 목적에 맞는 도구를 고르면 원본 노출 지점을 한 곳(CSV export)으로 줄일 수 있다.
- 개인정보 정책은 `PRIVACY.md` 문서로 고정해두고, 정책이 바뀔 때 코드와 문서를 함께 수정했다.
