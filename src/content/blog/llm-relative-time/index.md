> Calainder는 텍스트·이미지에서 일정을 뽑아 Google Calendar에 등록합니다. 날짜가 적힌 입력은 잘 처리됐지만 "4시간 뒤" 같은 상대시간이 엉뚱한 날짜로 나왔고, 이를 고친 것이 [#5](https://github.com/gasic37200/Calainder/issues/5)(v1.2.2)입니다. 이 글은 무엇을 기준으로 주고, 계산을 누구에게 맡길지 고른 과정입니다. 오류 경위는 프로젝트 페이지의 트러블슈팅에 있습니다.

## 배경과 제약

- **분석 흐름.** 화면 → Spring 서버 → FastAPI AI 모듈 → OpenAI API. AI 모듈이 프롬프트를 만들고 모델 응답(JSON 배열)을 그대로 돌려준다. 요청은 동기라 사용자는 응답을 기다린다.
- **입력은 텍스트와 이미지 두 가지.** 메신저 캡처 같은 이미지도 같은 모델로 분석한다.
- **사용자는 한국에 있다.** "4시간 뒤"는 한국 시간 기준이다.
- **서버는 AWS EC2 + Docker**였고, 나중에 OCI로 옮겼다.

결정 기준은 세 가지였습니다.

1. **기준 시각이 맞을 것** — 서버가 어디든 한국 시간 기준으로 계산한다.
2. **결과가 맞을 것** — 자정을 넘기는 계산까지 맞는다.
3. **비용과 구조** — 텍스트·이미지를 한 모델로 처리하고, 요청당 비용이 크게 늘지 않는다.

## 먼저 알아야 할 원리

### `datetime.now()`는 서버의 로컬 시간을 돌려준다

[Python `datetime` 문서](https://docs.python.org/3/library/datetime.html#datetime.datetime.now)에 따르면 `datetime.now()`에 시간대를 주지 않으면 `today()`처럼 **실행 중인 시스템의 로컬 시간**을 시간대 정보 없이(naive) 돌려줍니다. 시간대(`tzinfo`)를 넘기면 현재 시각을 그 시간대로 바꿔 돌려줍니다.

그래서 같은 코드라도 서버 시간대가 UTC면 UTC 시각이, KST면 KST 시각이 나옵니다. 실제로 EC2에서 `timedatectl`을 실행하니 `Time zone: Etc/UTC (UTC, +0000)`였고, AI 컨테이너도 UTC였습니다.

```python
from datetime import datetime
from zoneinfo import ZoneInfo

datetime.now()                        # 서버 로컬 시간 (EC2·컨테이너에선 UTC)
datetime.now(ZoneInfo("Asia/Seoul"))  # 서버와 상관없이 한국 시간
```

### 모델은 프롬프트에 적힌 것만 기준으로 삼는다

모델 요청에는 현재 시각이 따로 들어가지 않습니다. Calainder는 프롬프트 첫머리에 "오늘은 {today}입니다. 현재 시각은 {current_datetime}입니다."를 넣어 기준을 줍니다. 이 값이 9시간 어긋나 있으면 모델이 계산을 잘해도 결과가 9시간 어긋납니다.

### 모델 비교에 쓴 사실

[OpenAI 모델 문서](https://developers.openai.com/api/docs/models/gpt-4.1-mini)에서 gpt-4.1-mini는 텍스트와 **이미지 입력**을 받고, 1M 토큰당 입력 $0.40·출력 $1.60입니다. 당시 AI가 공식 자료를 근거로 gpt-4.1 계열이 지시 준수(instruction following)에서 gpt-4o 계열보다 낫다고 안내했고, gpt-4.1은 입력 $2.00·출력 $8.00으로 약 5배였습니다. 2026년 10월 다시 확인했을 때 이 문서는 gpt-4.1-mini를 deprecated로 표시하고 있습니다.

## 결정해야 했던 것

> **질문:** 상대시간을 맞게 바꾸려면 (1) 모델에 어떤 현재 시각을 어떻게 줄지, (2) 계산을 모델에 맡길지 서버가 할지, (3) 모델에 맡긴다면 어떤 모델을 쓸지.

다른 사용자가 05:20에 "5시간 뒤"를 넣었는데 13:20으로 나온 것이 시작이었습니다. 기준 시각을 고친 뒤에도 20:55에 "4시간 뒤"를 넣으니 다음 날 00:55가 아니라 같은 날 00:55로 나와, (2)와 (3)까지 정해야 했습니다.

## 검토한 선택지

### 현재 시각을 한국 시간으로 맞추는 위치

| 선택지 | 장점 | 단점 | 이 프로젝트에서 |
| --- | --- | --- | --- |
| EC2 시간대를 `Asia/Seoul`로 변경 | 로그 시각도 한국 시간이 됨 | 서버를 옮기면 다시 설정해야 함, 컨테이너는 별도 | 쓰지 않음 |
| Compose에 `TZ=Asia/Seoul` | 컨테이너 단위로 맞춤 | 설정이 빠지면 조용히 UTC로 돌아감 | 쓰지 않음 |
| **코드에서 `ZoneInfo("Asia/Seoul")` 명시** | 서버·컨테이너 설정과 무관 | 시간을 만드는 곳마다 명시해야 함 | **채택** |

AI는 "환경만 믿지 말고 코드에서 KST를 명시"하고, 필요하면 컨테이너 TZ도 맞추라고 순서를 제안했습니다. 코드 쪽만 적용했습니다.

### 상대시간 계산을 맡길 곳

| 선택지 | 장점 | 단점 | 이 프로젝트에서 |
| --- | --- | --- | --- |
| 모델 + 프롬프트 규칙 보강 | 코드 변경 없음, "다음 주 월요일" 같은 표현도 한 번에 처리 | 산술을 틀려도 그대로 화면에 나감 | 유지 |
| 서버가 `(\d+)시간 뒤`·`(\d+)분 뒤`를 정규식으로 찾아 계산해 덮어쓰기 | 정해진 패턴은 항상 맞음 | 패턴 밖 표현은 못 잡음, 모델 결과와 합치는 코드 필요 | AI가 제안, 검토만 하고 보류 |
| 모델 교체 | 코드 한 줄 | 비용 변화, 계산을 보장하지는 않음 | 함께 적용 |

### 모델

| 선택지 | 판단 |
| --- | --- |
| gpt-4o-mini 유지 | 기준 시각을 고친 뒤에도 "4시간 뒤"가 틀리게 나옴 |
| **gpt-4.1-mini** | 채택. 이미지 입력 지원, 지시 준수가 낫다는 안내, 비용 부담이 작음 |
| gpt-4.1 | 더 강하지만 약 5배 비용. 요청이 많아지면 부담이라 제외 |

## 이 방법을 고른 이유

- **기준 1(기준 시각):** 현재 시각을 코드에서 `Asia/Seoul`로 만들기 때문에 EC2든 OCI든, 컨테이너 시간대가 무엇이든 프롬프트에 들어가는 값이 같다.
- **기준 2(결과):** 종료 시각은 "명시가 없으면 시작 1시간 뒤", 자정을 넘을 때만 다음 날로 넘기는 규칙을 예시(22:48 → 23:48, 23:48 → 다음 날 00:48)와 함께 공통 프롬프트에 두었다. 그래도 틀린 계산은 모델을 바꾼 뒤 맞게 나와, 이 시점에는 서버 계산 코드를 더하지 않았다.
- **기준 3(비용과 구조):** gpt-4.1-mini는 이미지 입력을 받아 텍스트·이미지 분석을 한 모델로 유지했고, gpt-4.1 대신 골라 비용을 약 5분의 1로 두었다.

## 구현 코드

**현재 시각 만들기** (`calainder-ai/main.py`, [#5](https://github.com/gasic37200/Calainder/issues/5))

```python
def get_prompt_context() -> tuple[str, str]:
    now = datetime.now(ZoneInfo("Asia/Seoul"))     # 서버 시간대에 기대지 않음
    today = str(now.date())
    current_datetime = now.strftime("%Y-%m-%d %H:%M")
    return today, current_datetime
```

**공통 프롬프트의 시간 규칙** (`calainder-ai/prompts/common.py`, 발췌)

```text
오늘은 {today}입니다.
현재 시각은 {current_datetime}입니다.
상대시간 표현은 반드시 현재 시각 기준으로 계산해야 한다.
...
5. 사용자가 종료 일시를 직접 명시하지 않은 경우, 종료 일시는 시작 일시로부터 정확히 1시간 뒤이다.
8. 시작 시간에 1시간을 더했을 때 자정을 넘는 경우에만 end.date를 다음 날로 설정한다.
10. 예: start가 2026-05-19 23:48이면 end는 2026-05-20 00:48이다.
...
출력 전 최종 검토 규칙:
4. 상대시간으로 계산된 시작 일시를 기준으로 종료 일시를 다시 검산한다.
```

프롬프트는 처음에 텍스트·이미지 프롬프트에 같은 규칙이 따로 들어 있어, 공통 규칙(`common.py`)과 텍스트·이미지 전용 규칙으로 나눴습니다([#5](https://github.com/gasic37200/Calainder/issues/5)).

**모델 호출** — 텍스트·이미지 두 엔드포인트 모두 `client.responses.create(model="gpt-4.1-mini", ...)`.

## 구현하며 부딪힌 것

KST로 고친 코드를 올린 뒤에도 "4시간 뒤"가 같은 날 00:55로 나왔습니다. AI는 원인을 두 갈래로 나눠, AI 컨테이너 로그에 찍히는 `current_datetime`이 맞으면 모델의 계산 실수, 틀리면 배포가 반영되지 않은 것이라고 했습니다. 이 로그를 확인하지 않고 모델을 바꿔 다시 배포했고, 그 뒤 결과가 맞았습니다. 그래서 그 오류가 배포 반영 문제였는지 모델 실수였는지는 가르지 못했습니다.

## 검증

- 모델을 바꿔 다시 배포한 뒤, 배포 서버에서 상대시간 입력을 다시 넣어 결과가 맞는 것을 직접 확인했습니다.
- 몇 번, 어떤 입력으로 확인했는지 남긴 기록은 없습니다. PR [#5](https://github.com/gasic37200/Calainder/issues/5)의 확인 사항도 코드 기준 확인이고, 자동 테스트는 없습니다.

## 감수한 것과 다음

- **계산을 모델에 맡김.** "4시간 뒤"는 정해진 답이 있는 산술인데 모델이 계산합니다. 자정·월말을 넘는 입력에서 다시 틀리면, 서버가 `N시간 뒤·N분 뒤`를 직접 계산해 모델 결과를 덮어쓰는 방법(이번에 보류한 것)을 넣습니다.
- **회귀 테스트가 없음.** 현재 시각을 고정하고 "50분 뒤", "4시간 뒤", "오늘 밤 11시" 같은 입력의 결과를 확인하는 테스트가 있어야 모델을 바꿀 때 비교할 수 있습니다.
- **모델 수명.** gpt-4.1-mini가 deprecated로 표시돼 있어, 위 테스트를 기준으로 다음 모델을 골라야 합니다.

## 배운 점

- 모델이 알 수 없는 값(현재 시각, 시간대)은 서버가 계산해 명시해 넣는다. 그 값도 서버 환경에 기대지 않고 코드에서 시간대를 정한다.
- 정해진 답이 있는 계산을 모델에 맡기면, 맞게 나와도 "왜 맞았는지"를 설명할 수 없다. 결과를 확인할 테스트가 없으면 모델을 바꿀 때마다 같은 확인을 손으로 반복해야 한다.
- 원인이 두 갈래일 때는 갈라 볼 로그(`current_datetime`)를 먼저 보고 다음 변경을 한다. 둘을 함께 바꾸면 무엇이 고쳤는지 남지 않는다.
