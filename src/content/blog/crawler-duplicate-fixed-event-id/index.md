## 첫 번째 시도: DDING!

DDING!은 학교 홈페이지의 학식 메뉴를 크롤링해 MySQL에 저장하고 보여주는 서비스였습니다. 크롤러를 처음 다루던 시기라 **수집 이후 중복 여부를 판단하고 갱신하는 구조**를 설계하지 못했습니다.

그 결과 크롤러를 실행할 때마다 같은 메뉴가 다시 저장됐고, 이를 피하려고 **매번 SQL 데이터를 지운 뒤 크롤러를 다시 실행**하는 방식으로 대응해야 했습니다. 메뉴 테이블에는 메뉴 이름과 날짜의 unique 제약이 없었고, 스케줄러도 없어 크롤러를 수동으로 실행해야 했습니다.

> 크롤링은 데이터를 가져오는 것뿐 아니라 저장 기준, 갱신 기준, 실패 처리까지 함께 설계해야 한다.

## 두 번째 시도: Calainder

Calainder에서도 비슷한 문제가 생길 수 있는 지점이 있었습니다. E-Class의 과제 일정을 크롤링해 Google Calendar에 등록하는데, 사용자가 "과제 일정 업데이트"를 누를 때마다 **같은 과제가 캘린더에 또 등록**될 수 있었습니다.

이번에는 DDING!에서의 경험을 바탕으로, 같은 요청을 여러 번 보내도 결과가 같도록 만들었습니다.

1. 크롤링한 일정마다 **과목(`sub`) + 과제 제목(`title`)** 을 조합해 고정된 이벤트 ID를 생성
2. Google Calendar에 같은 ID의 이벤트가 **이미 있으면 수정**, 없으면 새로 등록

이 방식이면 크롤링을 몇 번 반복해도 캘린더에는 과제 하나당 일정 하나만 남고, 마감일이 바뀐 경우에는 기존 일정이 갱신됩니다. 크롤링 후에는 반영된 일정 목록을 다시 화면에 보여줘 사용자가 결과를 확인할 수 있게 했습니다.

ID 재료에서 마감일을 뺀 것은 마감이 바뀌면 ID도 바뀌어 다시 중복되기 때문이고, Google 이벤트 ID 문자 규칙(소문자 a~v, 숫자)에 맞추려고 SHA-256 해시를 썼습니다. 같은 ID로 다시 등록하면 충돌하므로, 등록 함수에서 ID가 있으면 먼저 조회해 있으면 수정하게 했습니다.

이 개선은 Calainder `release/v1.4.0`([PR #7](https://github.com/gasic37200/Calainder/issues/7))에 "E-Class 크롤링 일정 중복 방지"로 반영했습니다. PR에서는 고정 ID 생성까지 확인했고, 크롤링을 두 번 돌려 수정되는지 확인한 기록은 없습니다.

## 배운 점

- 외부 데이터를 주기적으로 가져오는 기능은 **"다시 실행해도 안전한가"** 를 먼저 설계해야 한다.
- 중복 판단 기준은 데이터 안에서 **변하지 않는 식별자**를 찾는 것에서 시작한다.
- 앞선 프로젝트의 실패를 기록해둔 덕분에, 다음 프로젝트에서 같은 문제를 설계 단계에서 막을 수 있었다.
