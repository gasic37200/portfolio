## 5. 개선안: 결과는 파일에, 규칙은 스킬에

### 5-1. "누가 시키나"보다 "어디로 모으나"

워크용이 지휘하는 계획도, 메인용을 따로 떼어 낸 계획도 결국 쓰이지 않은 걸 돌아보면, **누가 일을 시키는지는 규칙으로 지키기 어렵습니다.** 급하면 가장 가까운 세션에 말하게 됩니다. 대신 **결과를 어디로 모을지**를 정하면, 어디서 일했든 기록은 한곳에 모입니다.

메인 + 이슈 세션 구조에 기록을 맡는 **상주 정리용**을 둔다면, 결과를 모으는 방식은 둘입니다.

| 기준 | A. 동시 보고 (서브 → 메인 + 정리용) | B. 중계 (서브 → 정리용 → 메인) |
| --- | --- | --- |
| 메인이 결과를 아는 속도 | 바로 | 한 단계 늦음 |
| 메인 컨텍스트 (요청이 많을 때) | 보고가 올 때마다 길어짐 | 정리용이 묶어서 짧게 전달 |
| 서브의 보고 비용 | 두 번 작성 | 한 번 |
| 한 곳이 멈추면 | 다른 쪽에는 도착 | 정리용이 멈추면 메인이 모름 |
| 정리용의 부담과 왜곡 | 기록만 | 보고가 몰려 가장 먼저 길어지고, 요약하며 빠뜨리거나 지어낼 수 있음 |

요청이 많을 때는 **B가 메인을 지키는 데 유리**하지만, 3장에서 본 전달 실패·압축·지어냄이 모두 **정리용에 몰립니다.**

### 5-2. 섞어 쓰는 안

![결과를 메인, 정리용, 파일로 나눠 보내는 그림](/images/posts/session-orchestration/04-result-routing.svg)

| 받는 곳 | 보내는 내용 | 이유 |
| --- | --- | --- |
| 메인 | **한두 줄 신호** — "완료 / PR #12 / 결정 필요: 없음" | 짧게 유지하면서 바로 알고, 정리용이 멈춰도 안다 |
| 정리용 | **전체 보고** | 기록 정리는 정리용 몫 |
| 파일 (PR, 이슈, docs) | **실제 기록** | 세션은 압축되고 지워지지만 파일은 남는다 |

원칙은 두 가지입니다.

1. **기록은 세션이 아니라 파일에 남긴다.** 정리용은 기록을 보관하는 곳이 아니라 정리하는 일꾼이다.
2. **메시지는 세션 제목이 아니라 세션 ID로 보낸다.** 3-2에서 본 것처럼 이름은 헷갈릴 수 있다.

새 오케스트레이션 기능은 서브 세션이 끝나면 **결과 요약을 자동으로 메인에 돌려줍니다.** "서브 → 메인" 신호는 기본으로 생기니, 정리용 경로와 파일 기록만 정하면 됩니다.

### 5-3. 대화 기억에 기대던 규칙도 파일로

3-5에서 본 "이슈를 먼저 물어본다"는 규칙은 대화 기억에 기대고 있었습니다. 일회용 세션은 대화 기억이 없으니, **규칙도 사라지지 않는 곳으로** 옮겨야 합니다.

처음에는 "규칙을 전부 CLAUDE.md에 적자"고 생각했습니다. 그런데 친구 글에서 짚은 것처럼, **CLAUDE.md는 모든 세션이 시작할 때마다 통째로 읽힙니다.** 규칙을 쌓을수록 일회용 세션의 출발 비용이 커지고, 세션을 자주 만드는 B·C 방식에서 그 비용이 가장 크게 불어납니다. 공식 비용 문서도 CLAUDE.md는 200줄 이하로 두고, 특정 작업에만 필요한 지침은 **필요할 때만 불러오는 스킬로** 옮기라고 권합니다.

그래서 역할을 나눴습니다.

| 어디에 | 무엇을 | 언제 읽히나 |
| --- | --- | --- |
| **스킬** | 작업 규칙 본문 — 예: `git-issues`의 템플릿·라벨·중복 확인·확인 후 생성 | 그 작업을 할 때만 |
| **스킬 설명** | 언제 쓸지 — 예: "새 작업을 시작할 때 이슈부터 만들지 묻는다" | 항상 (짧은 한두 줄) |
| **CLAUDE.md** | 프로젝트 공통 핵심만 — 꼭 필요하면 "새 작업은 `git-issues`로 시작한다" 한 줄 | 모든 세션 시작 때 |

`git-issues`는 지금 직접 입력해야만 실행되는 설정이라, **Claude가 알아서 꺼내 쓰는 설정으로 바꾸고 설명에 "언제"를 적는 것**이 첫 번째 할 일입니다. 규칙 본문은 스킬에 그대로 두고, CLAUDE.md는 짧게 유지합니다. 결과는 파일에, **규칙은 스킬에** 두는 셈입니다.

### 5-4. 메인도 갈아 끼울 수 있게: 현황판과 최신화 스레드

B 방식에도 빈틈이 하나 남습니다. **메인 세션도 상주한다**는 점입니다. 보고와 결정이 쌓이면 메인도 결국 길어지고, 압축에 맡기면 3장에서 본 것처럼 정체성과 진행 상황을 잃을 수 있습니다. 그래서 압축을 잘하는 것보다 **압축해도 잃을 게 없게** 만드는 구조를 생각했습니다.

![현황판과 최신화 스레드로 메인 세션을 교체하는 흐름](/images/posts/session-orchestration/05-board-refresh.svg)

1. **메인이 이슈를 맡긴다.** 메인은 지휘만 하고 직접 작업하지 않는다.
2. **서브가 작업하면서 현황판에 기록한다.** 무엇을 했고, 무엇을 정했고, 무엇이 남았는지.
3. **서브는 메인에 신호만 보낸다.** "#12 완료, 기록함, 결정 필요: 없음". 오케스트레이션 기능은 서브가 끝나면 요약을 메인에 자동으로 돌려주므로, 서브에게 줄 규칙은 "현황판에 기록하기" 하나다.
4. **최신화가 필요하면 메인이 새 스레드를 연다.** 이 스레드가 현황판을 git·PR과 대조해 낡은 항목을 고치고, 진행 중 / 결정 대기 / 완료를 짧게 정리한다.
5. **정리를 읽은 새 스레드가 다음 메인이 된다.** 이전 메인은 압축하지 않고 보관한다.

**왜 압축 대신 교체인가** — 공식 문서에 따르면 압축은 대화 전체를 읽는 큰 요청이고, `/clear`로 새로 시작하는 건 비용이 없습니다. 상태가 현황판에 있으면 메인은 "기억하는 세션"이 아니라 **"현황판을 읽고 지휘하는 세션"**이 되고, 언제든 갈아 끼울 수 있습니다.

| 메인의 상태가 있는 곳 | 압축하거나 교체할 때 잃는 것 |
| --- | --- |
| 대화에만 있음 (지금까지의 방식) | **큼** — 정체성, 진행 중 작업, 결정의 이유 |
| 현황판에 있음 | **작음** — 잡담과 과정만 사라지고, 결정과 상태는 남음 |

#### 정해야 할 것 1: 현황판을 어디에 둘까

서브 세션은 보통 **별도 작업 공간(worktree), 별도 브랜치**에서 일합니다. 현황판이 저장소 안 파일이면, 서브가 적은 내용은 **그 서브의 브랜치에만** 있어서 머지 전까지 메인도 다른 서브도 못 봅니다. 여러 서브가 같은 파일을 고치면 머지할 때 충돌도 납니다. 3-4의 "같은 작업 폴더 공유" 문제가 형태만 바꿔 돌아오는 셈입니다.

| 현황판 위치 | 장점 | 단점 |
| --- | --- | --- |
| **GitHub 이슈 + 프로젝트 보드** | 서브가 자기 이슈에 댓글로 기록해 충돌이 없고, 팀원도 같이 본다. `git-issues`와 바로 이어진다 | 이슈 단위라 전체 요약은 따로 모아야 한다 |
| 저장소 밖 공유 파일 | 한눈에 보인다 | 동시에 쓰면 덮어쓸 위험이 있고, 팀원은 못 본다 |
| 저장소 안 파일 | 버전 관리된다 | 브랜치마다 따로 놀아서 위 문제가 생긴다 |

그래서 **서브는 자기 GitHub 이슈에 기록하고, 전체 요약판(`BOARD.md`)은 최신화 스레드만 고치는** 안이 가장 안전해 보입니다. 쓰는 쪽이 하나라 충돌이 없습니다.

#### 정해야 할 것 2: 요약과 현황판이 어긋나지 않게

메인에 보내는 요약과 현황판에 같은 내용을 따로 쓰면 언젠가 달라집니다. 메인에는 **내용이 아니라 신호만** 보내고, 내용의 원본은 현황판 한 곳에만 둡니다.

#### 정해야 할 것 3: 언제, 누가 메인이라는 걸 기억하나

- **시점** — 메인 컨텍스트가 40%쯤 찼을 때, 이슈 몇 개가 끝났을 때, 하루 한 번 중 하나로 정합니다. 너무 자주 하면 새 스레드의 시작 비용이 매번 듭니다.
- **역할** — "나는 메인이다, 현황판부터 읽는다"를 대화로만 설명하면 3-2의 메인용처럼 잊힐 수 있습니다. **메인 역할 스킬**로 만들어 두면 새 스레드가 시작할 때마다 읽습니다.

| | A. 역할별 상주 | B. 메인 + 일회용 | **B + 현황판 + 최신화 스레드** |
| --- | --- | --- | --- |
| 메인 | 없음 (그물 구조) | 상주, 길어지면 압축 | 주기적으로 새 스레드로 교체 |
| 기록 | 세션 대화 + 메모리 | 메인 대화 | 현황판 (GitHub 이슈 + 요약판) |
| 압축 손실 | 큼 | 메인에서 생김 | 거의 없음 (상태가 파일에) |
| 남는 비용 | 메시지마다 긴 대화를 다시 읽음 | 세션마다 시작 비용 | 세션 시작 비용 + 최신화 비용 |

이 구조는 아직 써 보지 않은 **설계**입니다. 다음 프로젝트에서 실제로 써 보고 6장 실험의 다음 편으로 이어 쓸 계획입니다.

## 6. 실험: 같은 크기 이슈 두 개로 비교하기

### 6-1. 설계

이 포트폴리오 사이트에 실제로 남은 작은 이슈 두 개를 골랐습니다. **서로 다른 파일**을 고쳐 동시에 해도 충돌하지 않습니다.

| | 이슈 A: 목록 화면 문구 한글화 | 이슈 B: 404 페이지 만들기 |
| --- | --- | --- |
| 방식 | **상주** — 메인 세션이 직접 처리 | **일회용** — 새 세션에 맡기고 끝나면 정리 |
| 내용 | `SHOWING 1 OF 4`, `ASCENDING`, `Tags` 등을 한글로 | 없는 주소에서 나오는 페이지를 사이트 디자인에 맞게 |
| 범위 | 기존 컴포넌트 2개 수정 | 새 페이지 1개 추가 |
| 완료 기준 | 빌드 통과 + 영어 문구 없음 | 빌드 통과 + 새 404 페이지 표시 |

두 이슈 크기가 완전히 같을 수는 없어서, 여유가 되면 **방식을 바꿔 한 번 더** 합니다.

**시작 비용을 따로 재는 이유** — 친구 글의 지적처럼 컨텍스트는 대화를 시작하기 전부터 차 있습니다. 이 글을 쓰는 세션에서 재 보니 첫 질문 전에 **시스템 도구 약 4%, MCP 도구 약 2%, 스킬 약 1%** 가 이미 차 있었습니다. 일회용 방식은 이 비용을 **세션마다** 내므로 따로 기록합니다.

**덧붙여 볼 조건 (C 방식 기준점)** — 상주 세션 쪽에 "컨텍스트 40%를 넘기 전에 수동으로 `/compact`한 경우"를 하나 더 둡니다. 친구가 쓰는 경험칙이 실제로 메인 세션 비용을 얼마나 줄이는지 함께 볼 수 있습니다.

**측정 항목**

| 항목 | 측정 방법 |
| --- | --- |
| 메인 세션 컨텍스트 증가량 | 작업 전후 메인 세션의 컨텍스트 토큰 차이 |
| 전체 사용량 | 작업 전후 5시간 사용량 % 차이 (이슈 세션 포함) |
| 이슈 세션 시작 비용 | 이슈 세션이 **아무 일도 하기 전**의 컨텍스트 토큰 (시스템 도구·MCP·스킬·CLAUDE.md가 차지한 몫) |
| 이슈 세션 컨텍스트 | 이슈 세션이 끝나기 직전의 컨텍스트 토큰 |
| 사람이 개입한 횟수 | 고쳐 달라고 요청한 횟수 |
| 첫 결과 품질 | 첫 결과로 완료 기준을 만족했는지 |
| 걸린 시간 | 요청부터 완료 확인까지 |

**공정하게 하기 위한 규칙** — 같은 형식(배경 → 할 일 → 완료 기준)으로 요청하고, 실험 중에는 다른 세션을 쓰지 않으며, 세션 컨텍스트는 작업 직후 바로 기록합니다.
