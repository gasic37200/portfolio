> **한눈에 보기**
>
> - JWT는 **Header.Payload.Signature** 세 부분을 점으로 이은 문자열이다. 앞의 두 부분은 Base64URL **인코딩일 뿐 암호화가 아니다.** 누구나 읽을 수 있다.
> - 서명은 내용을 숨기지 않는다. **내용이 바뀌지 않았다는 것**만 보장한다.
> - JWT는 서버가 따로 기억하지 않아서, 한 번 발급하면 **중간에 취소하기 어렵다.** 그래서 Access 토큰은 짧게, Refresh 토큰은 서버 저장소에 두고 쓸 때마다 바꾼다(회전).
> - 처음에는 "요청마다 서명과 Redis를 같이 확인한다"고 잘못 알았다. 요청마다 저장소를 보면 **결국 세션 방식**이다.
>
> 이 글은 JWT 자체를 다룬다. 이 토큰을 Spring Security가 요청마다 어떻게 검사하는지는 [2편: Spring Security에서 JWT 인증이 동작하는 흐름](/posts/spring-security-jwt)에서, Refresh 토큰을 둔 Redis는 [Redis 글](/posts/redis-in-replant)에서 이어집니다.

## 1. 세션 방식 vs 토큰 방식

![세션 방식은 요청마다 세션 저장소를 조회하고, 토큰 방식은 서명과 만료만 계산해서 확인하는 것을 비교한 그림](/images/posts/jwt-structure/04-session-vs-jwt.svg)

로그인 방식을 나누는 질문은 하나입니다. **서버가 "누가 로그인했는지"를 기억하는가?**

**세션 방식(stateful)** 은 서버가 기억합니다. 로그인하면 서버가 세션 저장소에 "abc123 → 회원 42"를 적고, 브라우저에는 `abc123`이라는 열쇠만 쿠키로 줍니다. 요청이 올 때마다 서버는 저장소에서 이 열쇠를 찾아봅니다.

**토큰 방식(stateless)** 은 서버가 기억하지 않습니다. 대신 토큰 안에 "회원 42, 30분 뒤 만료"를 적고 서명을 붙여 줍니다. 서버는 요청이 오면 저장소를 보지 않고 **서명과 만료 시간만 계산해서** 확인합니다.

| 기준 | 세션 방식 | 토큰 방식 (JWT) |
| --- | --- | --- |
| 로그인 상태를 아는 곳 | 서버의 세션 저장소 | 토큰 그 자체 |
| 요청마다 하는 일 | 저장소에서 세션 조회 | 서명·만료 계산 |
| 서버가 여러 대일 때 | 세션 저장소를 공유해야 함 | 같은 키만 있으면 됨 |
| 강제 로그아웃 | 세션을 지우면 바로 끝 | 토큰이 만료될 때까지 살아 있음 |
| 토큰이 새면 | 세션을 지워 막을 수 있음 | 만료 전까지 막기 어려움 |

어느 쪽이 더 좋다기보다 **무엇을 포기하는지가 다릅니다.** 세션은 "요청마다 조회"를 내고 "언제든 취소"를 얻습니다. JWT는 반대로 "조회 없음"을 얻고 "취소하기 어려움"을 냅니다. 5장의 Access/Refresh 분리는 이 약점을 메우려고 나온 방법입니다.

## 2. JWT의 세 부분

![JWT의 Header, Payload, Signature 세 부분과 각각에 들어가는 내용](/images/posts/jwt-structure/01-three-parts.svg)

JWT는 이렇게 생겼습니다. 점(`.`) 두 개로 세 부분이 나뉩니다.

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9      ← Header
.
eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIi...     ← Payload
.
SflKxwRJSMeKKF2QT4fw...                   ← Signature
```

실제로는 줄바꿈 없이 `Header.Payload.Signature` 한 줄로 이어져 있습니다.

### 2-1. Header: 어떻게 서명했나

```json
{ "alg": "HS256", "typ": "JWT" }
```

- `alg` — 서명 알고리즘입니다. 검증하는 쪽이 어떤 방법으로 서명을 다시 계산할지 알아야 해서 있습니다.
- `typ` — 이 토큰의 종류입니다. 보통 `JWT`입니다.

### 2-2. Payload: 누구의, 언제까지 유효한 토큰인가

Payload에 들어가는 항목 하나하나를 **클레임(claim)** 이라고 부릅니다. "이 토큰은 이렇다"는 주장이라는 뜻입니다.

[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)가 이름과 뜻을 정해 둔 **등록된 클레임**이 있습니다. 모두 선택 사항이지만, 이름을 맞춰 두면 라이브러리가 알아서 검사해 줍니다.

| 클레임 | 이름 | 뜻 |
| --- | --- | --- |
| `iss` | Issuer | 누가 발급했나 |
| `sub` | Subject | 누구에 대한 토큰인가 (보통 회원 ID) |
| `aud` | Audience | 누가 받아서 써야 하나 |
| `exp` | Expiration Time | 이 시각이 지나면 무효 |
| `nbf` | Not Before | 이 시각 전에는 무효 |
| `iat` | Issued At | 발급 시각 |
| `jti` | JWT ID | 토큰마다 붙이는 고유 ID (재사용 감지·블랙리스트에 씀) |

시각은 1970-01-01부터 지난 **초**(Unix 시간)로 적습니다.

등록된 이름이 아닌 클레임은 서비스끼리 약속해서 자유롭게 씁니다. `role`처럼 우리 서비스만 쓰는 값을 **비공개(private) 클레임**이라고 합니다.

### 2-3. Base64URL은 암호화가 아니다

가장 헷갈렸던 부분입니다. `eyJ...`로 시작하는 문자열이 암호처럼 보이지만, **Base64URL 인코딩**일 뿐입니다. 인코딩은 글자를 다른 글자로 바꿔 적는 규칙이라 **키 없이 누구나 되돌릴 수 있습니다.**

위 토큰의 Payload를 디코딩하면 바로 이렇게 나옵니다. (예시 값입니다)

```json
{
  "sub": "42",
  "role": "USER",
  "iat": 1792000000,
  "exp": 1792001800
}
```

`exp - iat = 1800`초, 즉 30분짜리 토큰이라는 것까지 누구나 알 수 있습니다.

그래서 **Payload에는 비밀번호, 주민등록번호, 전화번호 같은 민감정보를 넣지 않습니다.** 회원 ID와 권한처럼 "보여도 괜찮은 것"만 넣습니다.

> Base64URL은 일반 Base64에서 URL에 문제가 되는 `+`, `/`를 `-`, `_`로 바꾸고 끝의 `=`를 뺀 형식입니다. 토큰을 URL이나 헤더에 그대로 넣기 위해서입니다.

### 2-4. Signature: 위조 방지

Header와 Payload를 점으로 이은 문자열을 **비밀 키로 계산한 값**이 서명입니다. 다음 장에서 자세히 봅니다.

## 3. 서명이 하는 일

![HS256으로 발급할 때 서명을 만들고, 검증할 때 같은 키로 다시 계산해 비교하는 흐름](/images/posts/jwt-structure/02-sign-and-verify.svg)

Payload는 누구나 읽을 수 있으니, 누구나 `"sub": "42"`를 `"sub": "1"`로 바꿔 다시 인코딩할 수도 있습니다. 서명은 **이걸 막으려고** 있습니다.

1. 발급할 때 서버가 `header.payload`를 비밀 키로 계산해 서명을 붙인다.
2. 요청이 오면 서버가 받은 `header.payload`를 **같은 방법으로 다시 계산**한다.
3. 다시 계산한 서명과 토큰에 붙은 서명이 같으면 내용이 바뀌지 않은 것이다.

Payload를 한 글자만 바꿔도 계산 결과가 완전히 달라집니다. 비밀 키를 모르는 사람은 바뀐 Payload에 맞는 서명을 만들 수 없습니다.

정리하면 서명은 **무결성(안 바뀌었음)** 을 지킵니다. **내용을 숨기지는 않습니다.** 내용을 숨기려면 JWE라는 별도의 암호화 형식을 써야 하는데, 보통은 민감정보를 아예 넣지 않는 쪽을 택합니다.

### 3-1. HS256 vs RS256

| 기준 | HS256 | RS256 |
| --- | --- | --- |
| 방식 | HMAC-SHA256 (대칭 키) | RSA 서명 + SHA-256 (비대칭 키) |
| 서명할 때 | 비밀 키 | 개인 키 |
| 검증할 때 | **같은** 비밀 키 | 공개 키 |
| 키가 새면 | 누구나 토큰을 만들 수 있음 | 공개 키는 새도 괜찮음. 개인 키만 지키면 됨 |
| 잘 맞는 경우 | 발급하는 서버와 검증하는 서버가 같을 때 | 발급하는 곳(인증 서버)과 검증하는 곳(여러 서비스)이 다를 때 |

HS256은 검증하는 쪽도 비밀 키를 가져야 합니다. 그래서 검증하는 서버가 하나이거나 같은 팀 서버끼리만 쓸 때 간단합니다. 여러 서비스가 검증해야 한다면, 비밀 키를 여기저기 나눠 주는 대신 **공개 키만 나눠 주면 되는 RS256**이 안전합니다.

**알고리즘은 서버가 고정합니다.** 토큰 Header의 `alg`를 그대로 믿으면, 공격자가 `alg`를 `none`(서명 없음)으로 바꾼 토큰을 통과시킬 수 있습니다. 검증 코드에서 "이 서버는 HS256만 받는다"를 정해 둬야 합니다.

## 4. 검증 순서

서버는 토큰을 받으면 이 순서로 확인합니다.

1. **형식** — 점으로 나뉜 세 부분인가.
2. **알고리즘** — 서버가 정한 알고리즘(예: HS256)인가.
3. **서명** — 다시 계산한 서명과 같은가. 다르면 바로 401.
4. **클레임** — `exp`가 지나지 않았나, `nbf` 전이 아닌가, 필요하면 `iss`·`aud`가 맞나.

**서명을 먼저** 보는 이유가 있습니다. 서명이 맞지 않는 토큰의 `exp`는 누가 아무 값이나 적었을 수 있어서 믿을 근거가 없습니다. 내용이 진짜라는 걸 확인한 뒤에야 그 내용을 검사할 의미가 생깁니다. 보통은 라이브러리가 이 순서를 한 번에 처리해 줍니다.

## 5. Access 토큰과 Refresh 토큰

![로그인, 평소 요청, access 만료 후 refresh로 재발급하고 회전하는 흐름](/images/posts/jwt-structure/03-access-refresh-flow.svg)

### 5-1. 왜 둘로 나누나

1장에서 본 JWT의 약점은 **발급한 토큰을 서버가 중간에 취소하기 어렵다**는 것입니다. 서버가 아무것도 기억하지 않으니 "이 토큰은 무효"라고 적어 둘 곳이 없습니다.

그렇다고 토큰 수명을 짧게만 하면 사용자가 계속 다시 로그인해야 합니다. 그래서 역할을 둘로 나눕니다.

| 구분 | Access 토큰 | Refresh 토큰 |
| --- | --- | --- |
| 하는 일 | API 요청마다 "나 로그인했어" 증명 | Access가 만료되면 새로 받기 |
| 수명 | 짧게 (분 단위) | 길게 (일 단위) |
| 서버가 기억하나 | 안 함 (서명만 검사) | **함** (저장소에 둠) |
| 보내는 때 | 모든 API 요청 | 재발급 요청 때만 |

자주 오가는 Access는 짧게 해서 **새더라도 금방 쓸모없게** 만듭니다. 오래 쓰는 Refresh는 서버 저장소에 둬서 **서버가 지울 수 있게** 만듭니다. 두 장점을 섞은 구조입니다.

### 5-2. 재발급과 회전(rotation)

Access가 만료되면 서버는 401을 돌려줍니다. 클라이언트는 Refresh 토큰을 보내 새 Access를 받습니다.

**회전**은 이때 Refresh 토큰도 새것으로 바꾸고, **쓴 Refresh는 바로 폐기**하는 방식입니다.

- Refresh 토큰 하나는 **한 번만** 쓸 수 있다.
- 누가 옛 Refresh를 훔쳐 나중에 내밀어도, 저장소에 이미 없어서 거절된다.
- 일부 구현은 이미 쓴 Refresh가 다시 들어오면 "탈취"로 보고 그 사용자의 Refresh를 모두 지워 다시 로그인하게 한다.

### 5-3. 탈취됐을 때와 로그아웃

| 상황 | 대응 |
| --- | --- |
| Access가 새었다 | 만료까지 기다리는 수밖에 없다. 그래서 수명을 짧게 둔다 |
| Refresh가 새었다 | 저장소에서 지운다. 회전을 쓰면 옛 토큰은 이미 무효 |
| 로그아웃 | 저장소에서 Refresh를 지우고, 클라이언트도 토큰을 버린다 |
| Access까지 즉시 막아야 한다 | 블랙리스트(`jti` 등을 만료까지 저장)에 올리고 요청마다 확인 |

로그아웃해도 이미 나간 Access는 **남은 수명 동안은 유효**합니다. 이걸 즉시 막으려면 블랙리스트를 둘 수 있지만, 그러면 요청마다 저장소를 다시 보게 됩니다. 즉, 그만큼 세션 방식에 가까워집니다. 대부분은 "Access는 짧게, Refresh만 지운다"로 충분하다고 보고 넘어갑니다.

## 6. 토큰을 어디에 보관하나

| 보관 위치 | 장점 | 단점 |
| --- | --- | --- |
| `localStorage` | 새로고침해도 남는다. 쓰기 쉽다 | JS로 읽을 수 있어 **XSS**로 스크립트가 심어지면 그대로 훔쳐 간다 |
| JS 메모리(변수) | 페이지 밖에 남지 않는다 | 새로고침하면 사라진다(Refresh로 다시 받아야 함). XSS 중에는 여전히 쓰일 수 있다 |
| `HttpOnly` 쿠키 | JS가 읽을 수 없어 XSS로 **값을 훔치기** 어렵다 | 브라우저가 자동으로 실어 보내서 **CSRF**를 신경 써야 한다(`SameSite`, CSRF 토큰) |

- **XSS** — 공격자의 스크립트가 우리 페이지에서 실행되는 것. JS로 읽을 수 있는 곳에 둔 토큰은 다 위험하다.
- **CSRF** — 다른 사이트가 사용자의 브라우저를 이용해 우리 서버로 요청을 보내는 것. 쿠키는 자동으로 실리기 때문에 생긴다.

쿠키가 아닌 곳에 둔 Access 토큰은 요청마다 헤더에 직접 붙입니다.

```http
GET /api/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

`Bearer`는 "이 토큰을 **가진 사람**에게 권한을 준다"는 뜻입니다. 들고 있기만 하면 누구든 쓸 수 있으니, 보관 위치가 중요합니다.

정답 하나는 없습니다. 흔한 조합은 **Access는 메모리나 헤더로, Refresh는 `HttpOnly` 쿠키로** 두는 것입니다.

## 7. RePlant에서는 이렇게 했다

[RePlant Market](/projects/replant) 팀 프로젝트에서 우리 팀이 쓴 설정입니다. JWT와 Refresh 구현은 팀원이 맡았고, 나는 Redis 키와 TTL 규칙을 정했습니다.

### 7-1. 실제 설정

| 항목 | 설정 | 이유 |
| --- | --- | --- |
| Access 토큰 | 수명 30분, `Authorization: Bearer` 헤더로 전송 | 새더라도 30분 뒤엔 쓸모없게 |
| Access 검증 | 세션 없이(stateless) 요청마다 **서명만** 검사, Redis는 보지 않음 | 요청마다 저장소를 보지 않는 것이 JWT를 쓰는 이유 |
| 서명 | HS256, 비밀 키 `JWT_SECRET`은 서버 환경변수에만 | 발급과 검증을 같은 서버가 함 |
| 키 길이 | `JWT_SECRET`이 **32바이트 이상**이어야 앱이 뜸 | HS256에 맞는 길이(256비트)를 강제해, 짧은 키로 배포되는 실수를 시작 단계에서 막음 |
| Refresh 저장 | 원문 대신 **SHA-256 해시**로 Redis에 저장, 키 `auth:refresh:{tokenHash}` | Redis 내용이 보여도 원문 토큰을 바로 쓸 수 없게 |
| Refresh 수명 | 1일 = 쿠키 Max-Age = Redis TTL | 세 값이 어긋나면 "쿠키는 있는데 Redis엔 없는" 상태가 생김 |
| 재발급 | Redis `GETDEL`로 꺼내면서 지우고 새 토큰으로 교체 (회전) | 꺼내기와 지우기를 한 번에 해서, 같은 Refresh로 두 번 재발급되지 않게 |

### 7-2. 소셜 로그인 state는 쿠키에

소셜 로그인에서는 로그인 요청을 보낼 때 `state` 값을 만들어 두고, 돌아올 때 같은 값인지 확인합니다. 다른 사람이 만든 로그인 응답을 끼워 넣는 것을 막는 장치입니다.

우리 팀은 이 값을 Redis 대신 **쿠키**에 담았습니다. `HttpOnly`로 JS가 못 읽게 하고, 만료는 짧게 뒀습니다. `SameSite`는 `Lax`로 했습니다. 소셜 로그인 사이트에서 우리 사이트로 **돌아오는 이동**에도 쿠키가 실려야 하는데, `Lax`는 다른 사이트에서 링크로 넘어오는 GET 이동에는 쿠키를 보내 주기 때문입니다.

### 7-3. SSE 알림과 토큰 수명

실시간 알림(SSE)에는 문제가 하나 있었습니다. 브라우저의 `EventSource`는 **`Authorization` 헤더를 붙일 수 없습니다.** 그래서 우리 팀은 `fetch` 스트림으로 연결해 헤더를 붙였습니다.

또 SSE 연결은 한 번 열리면 오래 유지됩니다. 처음 연결할 때만 토큰을 검사하면, Access가 만료된 뒤에도 연결은 계속 살아 있게 됩니다. 그래서 **연결 수명을 Access 토큰 수명과 같은 30분**으로 맞췄습니다. 30분 뒤 다시 연결할 때 다시 검사받습니다.

SSE와 JWT 인증이 어디서 맞지 않는지는 [JWT로 인증하는 서버에 SSE 실시간 알림 붙이기](/blog/sse-jwt-async-dispatch)에 따로 정리했습니다.

### 7-4. 처음에 잘못 이해했던 것

처음에는 이렇게 이해했습니다.

> JWT를 쿠키에 담고, 요청마다 **서명과 Redis를 같이** 비교한다.

그런데 요청마다 서버 저장소를 조회한다면, 서버가 로그인 상태를 기억하는 **세션 방식과 다를 게 없습니다.** 토큰이 JWT 모양일 뿐입니다.

그래서 기준을 이렇게 바꿨습니다.

- Access 토큰은 **서명만** 본다. Redis를 보지 않는다.
- Redis에는 **서버가 기억했다가 지울 수 있어야 하는 것만** 둔다. Refresh 토큰이 그렇다.

이 기준이 서니 "왜 Refresh만 Redis에 있는지"가 자연스럽게 이해됐습니다.

## 헷갈릴 때 정리

- JWT의 Header·Payload는 **인코딩**이다. 누구나 읽는다. 민감정보는 넣지 않는다.
- 서명은 **위조 방지**다. 내용을 숨기지 않는다.
- 검증은 **서명 먼저, 클레임(`exp` 등) 나중**이다. 알고리즘은 토큰이 아니라 서버가 정한다.
- HS256은 같은 키로 서명·검증, RS256은 개인 키로 서명·공개 키로 검증한다.
- JWT는 발급 후 취소하기 어렵다. 그래서 **Access는 짧게, Refresh는 저장소에** 둔다.
- Refresh는 쓸 때마다 새것으로 바꾸고 옛것은 폐기한다(회전).
- 요청마다 저장소를 보면 그건 **세션 방식**이다. 저장소에는 지울 수 있어야 하는 것만 둔다.
- `localStorage`는 XSS에 약하고, 쿠키는 CSRF를 챙겨야 한다.
