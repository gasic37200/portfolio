> **한눈에 보기**
>
> - 팀 프로젝트에서 Claude Code 세션을 **역할별로 나눠 서로 연결해** 썼다. 어느 세션에서 말하든 직접 만든 `send-to` 스킬이 대화를 분석해 담당 세션으로 넘겼다.
> - 끝난 뒤 세션 8개에게 직접 물어보니, 동기화가 잘된 이유는 메시지가 아니라 **포크로 물려받은 대화, git 확인, 공유 메모리**였다.
> - 대신 **압축이 세션의 정체성까지 지웠고**, 잘 돌던 규칙 일부는 스킬이 아니라 **사라지는 대화 기억**에 기대고 있었다.
> - 공식 문서와 2026년 연구로 근거를 확인하고, 다른 두 방식과 비교할 질문을 세웠다. 개선안과 실험은 [2편](/posts/session-orchestration-2)에서 다룬다.

## 1. 세 가지 세션 운영 방식

![역할별 상주 세션, 메인과 이슈별 일회용 세션, 작업마다 새 스레드를 비교한 그림](/images/posts/session-orchestration/01-three-approaches.svg)

**A. 역할별 상주 세션 (내가 쓴 방식)** — [RePlant Market](/projects/replant) 팀 프로젝트(2026.10)에서 워크용, 인프라용, 정리용처럼 역할을 정한 세션을 여러 개 두고 **서로 연결해** 계속 이어서 썼습니다. 어느 세션에서 대화하든, 다른 세션 담당인 일이 나오면 세션이 대화를 분석해 그쪽으로 넘겼습니다.

프로젝트가 끝날 무렵, 다른 두 사람에게서 다른 방식을 들었습니다.

**B. 메인 + 이슈별 일회용 세션 (다른 팀 팀장의 방식)**

1. **메인 세션**을 하나 둔다.
2. 메인 세션에 이슈를 말하면 그 이슈를 위한 **새 세션이 만들어진다.**
3. 새 세션이 작업을 끝내고 결과를 메인에 돌려준다.
4. 끝난 세션은 **지운다.**

**C. 작업마다 새 스레드 (친구의 방식)** — 오케스트레이션 없이, 작업 하나마다 **새 스레드를 직접 열고 끝나면 지웁니다.** 한 스레드 안에서는 `/clear`와 수동 `/compact`로 컨텍스트를 관리하고, 사용량이 40%를 넘기 전에 정리합니다. 친구는 이 방식을 [긴 대화가 좋은 답변을 만든다는 착각](https://vanilalatte.tistory.com/entry/manage-context-ai-coding-tools)이라는 글로 정리했습니다.

B와 C는 모두 **세션을 짧게 쓰고 버린다**는 점에서 같고, B는 메인 세션이 그 일을 대신해 준다는 점이 다릅니다. 마침 Claude에 세션이 다른 세션을 만들고 결과를 돌려받는 **오케스트레이션** 기능이 생겨서, 이 방식들을 제대로 비교해 보기로 했습니다. 이 글은 주로 A와 B를 비교하고, C는 비교의 기준점으로 씁니다.

## 2. 내가 쓴 방식: 역할별 상주 세션

기획 대화를 하던 세션 하나를 **포크해서 역할별로** 나눴습니다.

| 세션 | 담당 |
| --- | --- |
| 워크용 | 기능 코드, API, 테스트 |
| 인프라용 | AWS, Docker, 배포, 환경변수 |
| 기획용 | 기획 문서 |
| 정리용 | 노션·ERD 정리, 의사결정 기록, PR 요약 |
| 리뷰용 | AI 리뷰 결과 정리 |
| 프론트용 | 프론트 화면 수정 |

### 처음 계획: 한곳에서 던지기

처음 계획은 **"요청은 전부 워크용에서 하고, 워크용이 다른 세션에 던진다"** 였습니다. 워크용이 기능 개발과 함께 메인 역할까지 맡는 구조였습니다.

그런데 한 세션에 기능 개발과 지휘가 섞이자, **메인 기능을 따로 떼어 내기로** 했습니다. 워크용에서 포크해 **메인용** 세션을 만들고, "어느 세션이 어떤 역할을 맡고, 메인용이 오케스트레이션처럼 전체를 관리한다"고 설명해 두었습니다. 사이드바에서도 메인용 아래에 나머지 세션을 묶어 한눈에 보려 했습니다.

이 계획도 그대로 되지는 않았습니다.

- 사이드바는 세션들을 메인용이 아니라 **정리용 아래로** 묶어 버렸습니다(이유는 3-1에서 나옵니다).
- 무엇보다 실제로 일할 때는 메인용을 거치지 않고, **해당 세션에 바로 이야기하는 게** 더 자연스러웠습니다. 워크용이 일하는 사이 인프라 할 일이 생기면 인프라용에 직접 말하는 식입니다.

그래서 메인용은 만들어 두고도 중심으로는 거의 쓰지 않았습니다.

### 실제로는: 서로 연결된 상주 세션

그래서 쓰다 보니 **모든 상주 세션이 서로 연결된** 구조가 됐습니다. 어느 세션에서 대화하든, 직접 만든 `send-to` 스킬이 **대화를 분석해** "이건 인프라용 담당이니 넘길게요"라고 판단하고 그 세션으로 일을 넘겼습니다.

![send-to 스킬로 세션 사이에 일을 넘기는 흐름](/images/posts/session-orchestration/02-send-to-flow.svg)

1. 대화 주제가 다른 세션 담당이면 "인프라용 담당이에요. 보낼까요?"라고 한 줄로 묻는다.
2. 같은 폴더의 세션 목록에서 제목에 역할 이름이 들어간 세션을 찾는다.
3. 받는 세션은 이 대화를 모르므로, **메시지만 읽고 바로 일할 수 있게** 요청·맥락·다음 할 일을 요약해 보낸다.
4. 받은 세션은 git·PR로 현재 상태를 확인하고 일한다.
5. 끝나면 `[완료 보고]`로 결과를 돌려보낸다.

중심 세션 없이 각 세션이 라우터 역할을 나눠 맡은 셈입니다. 프로젝트는 잘 끝났습니다. 쓰는 동안 **동기화가 잘되는 느낌**이었고, 중간에 컨텍스트 압축이 있었지만 잃은 건 많지 않다고 느꼈습니다. 다만 정형화된 방식이라기보다 임기응변으로 쓰는 느낌이 남아서, 이 체감이 맞는지 확인해 보기로 했습니다.

## 3. 뜯어보니: 세션 8개에게 직접 물어본 결과

각 세션에게 같은 질문을 보내 **자기 대화 기록을 근거로** 답하게 했습니다. 어디서 태어났는지, 메시지를 받으면 어떻게 행동했는지, 압축으로 무엇을 잃었는지를 물었습니다.

### 3-1. 모두 한 세션에서 갈라졌다

![세션 9개의 포크 계보](/images/posts/session-orchestration/03-fork-lineage.svg)

세션 기록 파일을 비교해 보니 9개 세션 모두 **앞부분 기록(10/01 ~ 10/07)이 똑같았습니다.** 포크는 원래 대화를 **통째로 복사**합니다.

- 동기화가 잘된 느낌의 일부는 메시지 덕분이 아니라 **포크하면서 이전 대화를 물려받은 덕분**이었다.
- 반대로 각 세션은 시작부터 긴 대화를 안고 출발했다.
- 사이드바에서 메인용 아래로 묶으려던 세션들이 **정리용 아래로** 묶인 것도 누가 정한 게 아니라, **앱이 포크 계보를 트리로 보여 준 것**이었다. 정리용이 다른 세션들의 조상이었기 때문이다. 보이는 구조, 계획한 구조, 실제로 쓴 구조가 모두 달랐다.

### 3-2. 압축이 "내가 누구인지"를 지웠다

세션마다 압축(자동 요약)이 1~3회 있었고, 그 뒤 **자기 역할을 잘못 아는 세션**이 여럿 나왔습니다.

| 세션 | 스스로 안 것 | 실제 |
| --- | --- | --- |
| 메인용 | "나는 워크용" (압축 요약에 그렇게 적혀 있음) | 워크용에서 갈라진 사본 |
| 기획용 | 압축 요약에 "워크용"으로 기록 | 워크용에서 포크된 세션 |
| 워크용, 인프라용 | "처음부터 만든 세션 같다" | 포크 (요약에서 대화가 시작돼 출생 기록을 못 봄) |

포크하면 요약 속 "나는 워크용"까지 복사됩니다. 메인용은 만들 때 "오케스트레이션처럼 관리하는 세션"이라고 역할을 설명해 뒀는데도, 조사해 보니 **압축 요약 기준으로 자기를 워크용으로 알고 있었습니다.** 그래서 메시지에 보낸 세션을 "워크용"으로 적었고, **완료 보고가 엉뚱한 세션으로 갈 수 있는** 상태였습니다. 역할을 대화로 설명하는 것만으로는 압축을 넘어 유지되지 않을 수 있다는 뜻입니다.

압축으로 잃은 것은 이랬습니다.

- **세션 정체성** (위 표)
- **메시지 원문과 정확한 날짜, 도구 실행 결과 원문**
- **구체적인 사실 하나** — "OrderService가 ShipmentService를 직접 호출한다"가 빠져, 리팩터링 뒤 **컴파일 에러로 뒤늦게** 발견
- **없던 문장** — 정리용이 요약 뒤 원문에 없던 문구를 지어 넣었다가 지움

"잃은 게 많지 않았다"는 체감은 **결정 사항에 한해서는** 맞았습니다. 결정은 메모리 파일과 docs에 적어 둬서 살아남았지만, 세부 사실과 정체성은 실제로 사라졌습니다.

### 3-3. 메시지는 출발점, 기준은 git이었다

잘 작동한 부분도 있었습니다. 거의 모든 세션이 메시지를 받으면 **바로 작업하지 않고 확인부터** 했습니다.

- `git fetch`, `git grep`, PR·이슈, 노션 페이지로 현재 상태를 확인했다. 워크용은 메시지에 적힌 "구매자만 호출한다"를 `git grep`으로 직접 검증했다.
- 운영 DB 보정 SQL 요청을 받은 인프라용은 위험 요소를 확인하고 **머지될 때까지 보류**했다.
- 이슈 생성, push, PR은 사용자가 승인한 뒤에만 했다.

같은 프로젝트의 세션들은 **메모리 파일을 공유**해서, 한 세션이 적은 결정("ElastiCache는 쓰지 않는다")을 다른 세션이 다시 시작할 때 읽었습니다. 동기화가 잘된 진짜 이유는 **각 세션이 git과 공유 메모리를 기준으로 상태를 다시 맞췄기 때문**이었습니다.

### 3-4. 그래도 생긴 동기화 문제

| 문제 | 실제 사례 |
| --- | --- |
| 같은 작업 폴더 공유 | 메인용이 워크용의 커밋 안 된 파일을 고침. 워크용이 테스트하는 동안 같은 폴더에서 머지 |
| 낡은 메시지 | 보낸 요청이 사용자 결정으로 취소됨. 보정 SQL이 데이터 재적재로 필요 없어짐 |
| 최신 코드를 안 받음 | `git fetch` 없이 "SSE는 아직 없다"고 답했다가 정정 |
| 결정이 엇갈림 | 리프레시 토큰 TTL이 14일 / 1일 / 3시간으로 세 곳에서 다름 |
| 완료 보고 누락 | 프론트용은 꼬박꼬박 돌려보냈지만 인프라용은 한 번도 보내지 않음 |
| 전달 실패 | 받는 세션이 20초 안에 시작하지 않아 메시지가 전달되지 않음 |

인프라용은 매번 별도 작업 공간(worktree)을 써서, 같은 폴더 충돌을 겪지 않았습니다.

### 3-5. 내가 믿었던 것과 실제

조사하다 보니 직접 만든 스킬이 해 준다고 믿었던 동작 중 일부는 **다른 이유로** 일어나고 있었습니다. 먼저 헷갈리기 쉬운 말을 나눕니다.

| 용어 | 뜻 | 사라지는 때 |
| --- | --- | --- |
| 스킬 | 일을 **어떻게** 할지 적은 문서 | 사라지지 않음 |
| 스킬 호출 방식 | **언제** 꺼낼지. 직접 입력해야만 실행 / Claude가 알아서 꺼내 씀 | 사라지지 않음 |
| 대화 기억 | 세션 안의 대화. 포크하면 그대로 복사됨 | 압축되면 흐려지고, 새 세션엔 없음 |
| 메모리 파일·문서 | 파일에 적어 둔 결정과 규칙 | 사라지지 않음 |

| 체감한 동작 | 믿었던 이유 | 실제 이유 |
| --- | --- | --- |
| 세션끼리 동기화가 잘됨 | `send-to` 메시지 | 포크로 물려받은 대화 + git 확인 + 공유 메모리 |
| "보낼까요?"라고 물어봄 | `send-to` 스킬 | **실제로 스킬 덕분** (Claude가 알아서 꺼내 쓰는 설정) |
| "이슈 만들까요?"라고 물어봄 | `git-issues` 스킬 자동 실행 | **포크로 물려받은 대화** (`git-issues`는 직접 입력해야만 실행되는 설정) |
| `grill-me`가 자동으로 불러와짐 | 스킬이 알아서 실행 | **직접 입력**한 `grill-me`가 자동 실행 스킬 `grilling`을 불러옴 |

"이슈 만들까요?"는 9개 세션 기록 모두에 같은 설명으로 남아 있었습니다. 포크 전 원본 세션에서 나눈 대화가 복사됐고, 각 세션은 그 **대화 기억**을 보고 물어본 것입니다. 그래서 이 동작은 **새 프로젝트나 포크하지 않은 새 세션에서는 재현되지 않습니다.**

`git-issues` 스킬 자체는 쓸모가 있었습니다. 템플릿·라벨·제목 형식을 따르고, 이미 된 일을 빼고, 확인 후에만 생성하는 **"어떻게"** 를 정해 줬고, 이슈 18개를 이 스킬로 만들었습니다. 빠진 건 **"언제"** 였습니다. 덧붙여 스킬의 로컬 기록에 "진행 중"으로 남은 이슈 8개는 GitHub에서 모두 닫혀 있었습니다. **기준은 항상 GitHub이어야 합니다.**

> **3장 정리** — 상주 세션의 문제는 "길어진다"에서 끝나지 않았다. 포크로 물려받은 긴 대화, 압축이 지운 정체성, 같은 폴더 공유, 낡은 메시지가 함께 있었고, 잘 돌던 규칙 일부는 **사라지는 대화 기억**에 기대고 있었다. 반대로 **메시지를 믿지 않고 git으로 확인하는 습관**과 **결정을 파일에 적는 습관**은 어떤 방식에서든 지켜야 한다.

## 4. 근거: 공식 문서와 최신 연구

두 방식을 그대로 비교한 공개 자료는 없었습니다. 모델과 도구가 빠르게 바뀌어서, 1년 전 연구의 숫자도 지금 세션에 그대로 옮길 수 없었습니다. 그래서 **지금 동작을 설명하는 공식 문서**와 **최신 모델로 한 연구**를 근거로 삼았습니다. (2026년 10월 기준)

### 4-1. 공식 문서: 세션이 토큰을 쓰는 방식

Claude Code 공식 문서 [Manage costs effectively](https://code.claude.com/docs/en/costs)에서 이 글과 이어지는 내용입니다.

| 문서 내용 | 이 글과의 연결 |
| --- | --- |
| 다른 세션에서 온 메시지는, 받는 세션이 쉬고 있으면 **새 턴으로 전달되고 매번 전체 컨텍스트를 다시 보낸다** | `send-to`로 길어진 상주 세션에 보낼 때마다 그 긴 대화 전체를 다시 읽는다 |
| 긴 세션은 한 줄짜리 질문에도 대화 전체만큼 사용량이 든다. 압축도 큰 요청이고, `/clear`는 비용이 없다 | 상주 세션이 길어질수록 모든 요청이 비싸진다 |
| 서브에이전트는 장황한 결과를 자기 안에 두고 **요약만 메인으로 돌려준다**. 서브에이전트의 요청도 사용량에 들어간다 | 일회용 방식이 메인을 짧게 지키는 원리이자 비용 |
| 에이전트 팀은 팀원이 계획 모드로 돌 때 **일반 세션보다 토큰을 약 7배** 쓴다 | 나눠 맡길수록 늘어나는 토큰의 공식 수치 |
| 팀원 세션은 시작할 때 CLAUDE.md, MCP 서버, 스킬을 **자동으로 읽는다** | 새 세션은 대화 기억이 아니라 **파일로** 맥락을 받는다 |

상주 방식은 **"요청마다 긴 대화를 다시 읽는 비용"**, 일회용 방식은 **"세션마다 처음부터 맥락을 읽는 비용"** 을 냅니다. 어느 쪽도 공짜가 아닙니다.

### 4-2. 최신 연구: 컨텍스트가 길면 놓치는 게 늘어난다

[Classifier Context Rot](https://arxiv.org/abs/2605.12366)(2026.05)는 **Opus 4.6, GPT 5.4, Gemini 3.1**에게 코딩 에이전트의 작업 기록을 보여 주고 위험한 행동을 찾게 했습니다. 같은 행동이라도 **80만 토큰의 정상 작업 뒤에** 나오면 **2배~30배 더 자주 놓쳤고**, 기록 중간중간 주의를 환기하는 프롬프트로 일부 완화됐습니다.

"상주 세션이 길어지면 요점이 흐려진다"는 체감을 최신 모델로 뒷받침합니다. 다만 위험 행동 감지 과제라, 일반 개발 작업의 품질 저하와 같다고 단정할 수는 없습니다.

<details>
<summary><strong>배경: 1년 전 연구도 같은 방향이었다</strong></summary>

- Chroma의 [Context Rot](https://www.trychroma.com/research/context-rot)(2025.07) — 당시 모델 18개에서 입력이 길수록 성능이 불안정해졌다.
- Anthropic의 [멀티 에이전트 리서치 시스템](https://www.anthropic.com/engineering/multi-agent-research-system)(2025.06) — 일을 나눠 맡긴 구조가 더 좋은 결과를 냈지만 토큰을 훨씬 많이 썼다. 리서치 작업과 이전 세대 모델 기준이라 숫자는 참고만 한다.

</details>

### 4-3. 그래서 남은 질문

| 기준 | 역할별 상주 세션 | 이슈별 일회용 세션 |
| --- | --- | --- |
| 컨텍스트 길이 | 계속 길어짐 (압축 발생) | 이슈 하나 분량으로 짧음 |
| 맥락 유지 | 세션 안에 쌓임 | 매번 새로 시작 → 파일로 넘겨줘야 함 |
| 토큰 | 요청·메시지마다 긴 대화를 다시 읽음 | 세션마다 CLAUDE.md·스킬·저장소를 처음부터 읽음 |
| 사람이 할 일 | 어느 세션에 말할지 고르기 | 메인 세션에 이슈만 말하기 |
| 기록 | 세션 대화에 남음 | 세션이 지워지므로 PR·문서로 남겨야 함 |

**"그럼 내 작업 규모에서는 어느 쪽이 이득인가?"** 공식 문서의 7배는 에이전트 팀 기준이고 논문은 감지 과제라서, 작은 개발 이슈에서의 차이는 직접 확인해야 했습니다.
