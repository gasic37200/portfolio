> **한눈에 보기**
>
> - 상태 코드는 **첫 자리**가 가장 중요하다. 2xx 성공, 4xx 요청 쪽 문제, 5xx 서버 쪽 문제.
> - **401은 "누구인지 모름"**, **403은 "누구인지 알지만 권한 없음"**, **404는 "없음"**이다. 남의 것은 404로 존재 자체를 숨기기도 한다.
> - 형식이 틀리면 400, 형식은 맞는데 처리할 수 없는 내용이면 422, **지금 상태와 부딪히면 409**다.
> - 클라이언트는 보통 **5xx·408·429만 다시 시도**한다. 4xx는 다시 보내도 결과가 같기 때문이다.
> - RePlant 프로젝트에서 실제로 고른 코드와 그 이유를 예로 붙였다.

## 1. 상태 코드는 세 자리, 첫 자리가 가족이다

상태 코드는 서버가 "요청을 어떻게 처리했는지"를 숫자 세 자리로 알려 주는 값입니다. 첫 자리가 **가족(class)** 을 정하고, 나머지 두 자리가 구체적인 이유를 정합니다.

![1xx부터 5xx까지 상태 코드 다섯 가족과 대표 코드](/images/posts/http-status-codes/01-families.svg)

| 가족 | 뜻 | 한 줄로 |
| --- | --- | --- |
| 1xx | 정보 (Informational) | 요청을 받았고 아직 처리 중이다 |
| 2xx | 성공 (Successful) | 요청을 제대로 처리했다 |
| 3xx | 리다이렉션 (Redirection) | 일을 끝내려면 클라이언트가 한 번 더 움직여야 한다 |
| 4xx | 클라이언트 오류 (Client Error) | 요청에 문제가 있다 |
| 5xx | 서버 오류 (Server Error) | 서버가 요청을 처리하지 못했다 |

첫 자리가 중요한 이유가 있습니다. RFC 9110에 따르면 클라이언트는 **모르는 코드를 받으면 그 가족의 x00 코드처럼 다뤄야** 합니다. 예를 들어 처음 보는 `471`을 받아도 `400`처럼 처리하면 됩니다. 그래서 세부 코드가 애매할 때도 **가족만큼은 정확히** 골라야 합니다.

1xx는 백엔드 API를 만들면서 직접 고를 일이 거의 없습니다. 웹소켓으로 넘어갈 때 쓰는 `101 Switching Protocols` 정도만 알아 두면 됩니다.

## 2. 자주 쓰는 코드 한 장 정리

| 코드 | 공식 문구 | 한 줄 뜻 | 언제 쓰나 |
| --- | --- | --- | --- |
| 200 | OK | 성공했고, 결과를 본문에 담았다 | 조회 성공, 그 밖의 일반적인 성공 |
| 201 | Created | 성공했고, 새 리소스를 만들었다 | 회원 가입, 주문 생성처럼 새것을 만들었을 때. 보통 `Location` 헤더로 새 주소를 알려 준다 |
| 204 | No Content | 성공했고, 돌려줄 본문이 없다 | 삭제, "모두 읽음"처럼 결과만 알리면 될 때 |
| 301 | Moved Permanently | 주소가 영구히 바뀌었다 | 도메인·URL 구조를 영구히 옮겼을 때 |
| 302 | Found | 지금은 잠깐 다른 주소에 있다 | 로그인 뒤 원래 페이지로 보내기 같은 임시 이동 |
| 304 | Not Modified | 가진 사본을 그대로 써도 된다 | 조건부 요청(`If-None-Match` 등)에 바뀐 게 없을 때. 본문을 보내지 않는다 |
| 400 | Bad Request | 요청 자체가 잘못됐다 | JSON 문법 오류, 필수값 누락, 허용하지 않는 값 |
| 401 | Unauthorized | 누구인지 확인하지 못했다 | 토큰·API 키가 없거나 틀리거나 만료됐을 때 |
| 403 | Forbidden | 누구인지 알지만 허락할 수 없다 | 로그인은 했지만 그 일을 할 권한이 없을 때 |
| 404 | Not Found | 대상을 찾을 수 없다 | 없는 id, 없는 경로. 존재를 숨기고 싶을 때도 |
| 405 | Method Not Allowed | 그 주소에 그 메서드는 안 된다 | `GET`만 되는 주소에 `DELETE`를 보냈을 때. `Allow` 헤더로 되는 메서드를 알려 줘야 한다 |
| 408 | Request Timeout | 요청을 끝까지 받기 전에 서버가 기다리다 지쳤다 | 클라이언트가 요청을 너무 느리게 보낼 때 (주로 서버·프록시가 자동으로 보냄) |
| 409 | Conflict | 리소스의 현재 상태와 부딪힌다 | 이미 처리된 주문 취소, 같은 키로 다른 요청 |
| 415 | Unsupported Media Type | 이 본문 형식은 받지 않는다 | JSON만 받는데 `Content-Type: text/plain`으로 보냈을 때 |
| 422 | Unprocessable Content | 형식은 맞는데 내용을 처리할 수 없다 | 문법은 맞지만 값의 의미가 맞지 않을 때. 예전 이름은 Unprocessable Entity |
| 429 | Too Many Requests | 너무 자주 요청했다 | 요청 횟수 제한(rate limit)에 걸렸을 때. `Retry-After`로 언제 다시 올지 알려 줄 수 있다 |
| 500 | Internal Server Error | 서버 안에서 예상하지 못한 문제가 생겼다 | 잡지 못한 예외, 버그 |
| 502 | Bad Gateway | 내가 부른 윗단 서버가 이상한 응답을 줬다 | 프록시·게이트웨이 뒤의 서버가 죽었거나 잘못 응답할 때 |
| 503 | Service Unavailable | 지금은 처리할 수 없다 (일시적) | 과부하, 점검 중. `Retry-After`를 함께 보낼 수 있다 |
| 504 | Gateway Timeout | 윗단 서버의 응답을 기다리다 시간이 다 됐다 | 프록시·게이트웨이 뒤의 서버가 너무 느릴 때 |

두 가지만 덧붙입니다.

- `422`는 원래 WebDAV 규격에서 Unprocessable Entity라는 이름으로 나왔고, RFC 9110에서 **Unprocessable Content**라는 이름으로 일반 HTTP 코드가 됐습니다. 오래된 자료나 프레임워크 상수에는 옛 이름이 남아 있습니다.
- `429`는 RFC 9110이 아니라 **RFC 6585**에 정의된 코드입니다. 그래도 지금은 어디서나 쓰입니다.

## 3. 401 vs 403 vs 404: 가장 자주 헷갈리는 셋

![401은 누구인지 모름, 403은 권한 없음, 404는 대상 없음을 비교한 그림](/images/posts/http-status-codes/02-401-vs-403-vs-404.svg)

이름부터 함정입니다. `401`의 공식 문구는 **Unauthorized**인데, 실제 뜻은 "권한 없음"이 아니라 **"인증 안 됨"** 입니다.

| 코드 | 서버의 속마음 | 다시 로그인하면? |
| --- | --- | --- |
| 401 | "당신이 **누구인지 모르겠다**" | 풀린다 (올바른 인증 정보를 보내면 된다) |
| 403 | "누구인지는 **알지만 이 일은 안 된다**" | 그대로다 (권한이 바뀌어야 한다) |
| 404 | "그런 **대상이 없다**" (또는 있다고 말해 주지 않겠다) | 그대로다 |

용어로 나누면 이렇습니다.

- **인증(Authentication)**: 너는 누구냐. 실패하면 `401`.
- **인가(Authorization)**: 너는 이걸 해도 되냐. 실패하면 `403`.

규격상 `401`을 보낼 때는 어떤 방식으로 인증해야 하는지 알려 주는 `WWW-Authenticate` 헤더를 함께 보내야 합니다. 브라우저용 API에서는 자주 빠지지만, 원래 이 헤더까지가 `401`의 짝입니다.

### RePlant에서 고른 코드

**401: 택배사 웹훅의 API 키 검사.** [RePlant](/projects/replant)에서 택배사가 배송 상태를 알려 주는 웹훅은 `X-Api-Key` 헤더로 보낸 쪽을 확인합니다. 키가 틀리거나, 없거나, **서버에 키가 설정되지 않았으면** 본문 없이 `401`을 돌려줍니다. 서버에 키가 없을 때도 "누구인지 확인할 수 없다"는 점은 같기 때문입니다.

**404: 남의 알림 읽음 처리.** 다른 사람의 알림 id로 읽음 처리를 요청하면, 권한 문제니까 `403`이 맞아 보입니다. 하지만 RePlant는 `404 NOTIFICATION_NOT_FOUND`를 돌려줬습니다. `403`을 주면 "그 id의 알림이 **있기는 하다**"는 사실이 새어 나가기 때문입니다.

이 방식은 규격도 허용합니다. RFC 9110은 금지된 대상의 **존재를 숨기고 싶은 서버는 403 대신 404로 답해도 된다**고 적고 있습니다.

> 남의 리소스를 건드리는 요청에서 **존재 자체가 정보**라면 404, 존재를 알려 줘도 괜찮고 "권한이 없다"고 분명히 말해 주는 편이 낫다면 403입니다.

### 프레임워크가 대신 고르는 401·403

직접 고르지 않아도 프레임워크가 `401`·`403`을 보내기도 합니다. RePlant에서 Spring Security를 쓸 때, **SSE로 알림을 보내는 과정**에서 `401`·`403`이 날 수 있었습니다. SSE 전송이 비동기 디스패치로 다시 필터를 지나는데, 그때 **인증 정보가 비어 있어** 보안 필터가 막은 것입니다.

내 코드가 `401`·`403`을 던지지 않았는데 그 코드가 보인다면, **인증 필터가 언제, 어떤 스레드에서 돌았는지**부터 의심해 볼 만합니다.

## 4. 400 vs 422 vs 409: "요청이 틀렸다"의 세 갈래

셋 다 "요청을 처리할 수 없다"지만 **어디가** 문제인지가 다릅니다.

| 코드 | 무엇이 문제인가 | 예 |
| --- | --- | --- |
| 400 Bad Request | 요청이 **잘못 만들어졌다** | JSON이 깨짐, 필수값 없음, 허용하지 않는 값 |
| 422 Unprocessable Content | 형식은 맞는데 **내용을 처리할 수 없다** | JSON 문법은 맞지만 값끼리 말이 안 맞음 |
| 409 Conflict | 요청은 멀쩡한데 **리소스의 지금 상태**와 부딪힌다 | 이미 수거된 배송을 취소 |

`400`과 `422`의 경계는 팀마다 다릅니다. 검증 실패를 전부 `400`으로 보내는 팀도 많고, 형식 오류는 `400`·값 검증 실패는 `422`로 나누는 팀도 있습니다. 중요한 건 **한 프로젝트 안에서 한 가지 규칙을 지키는 것**입니다. 반면 `409`는 경계가 분명합니다. **같은 요청이라도 리소스 상태에 따라 성공할 수도 있었다면** `409`입니다.

### RePlant에서 고른 코드

- **400 `ONLY_READ_SUPPORTED`**: 알림 읽음 처리 API에 `isRead: false`를 보내면 `400`을 줍니다. 이 API는 "읽음으로 바꾸기"만 지원하므로, `false`는 **허용하지 않는 값**입니다. 알림 상태가 어떻든 결과가 같으니 `409`가 아닙니다.
- **409 `SHIPMENT_NOT_CANCELABLE`**: 택배가 **이미 수거된 뒤** 배송을 취소하면 `409`입니다. 수거 전이었다면 같은 요청이 성공했을 것입니다.
- **409 `SHIPMENT_NOT_DELIVERED`**: 배송이 **완료되기 전에** 구매 확정을 누르면 `409`입니다. 배송이 끝나면 같은 요청이 성공합니다.

두 `409`는 모두 "요청은 맞지만 **지금은** 안 된다"입니다. 이 차이를 에러 코드 문자열(`SHIPMENT_NOT_CANCELABLE` 등)로 한 번 더 구분해 두면, 프론트가 상태 코드만 보고 헤매지 않습니다.

### 프레임워크가 대신 고르는 422

[Teammate](/projects/teammate) 프로젝트에서는 FastAPI가 요청 본문을 **비어 있는 것으로 받아** `422`를 돌려준 적이 있습니다. FastAPI는 요청 검증에 실패하면 기본으로 `422`를 보냅니다. 그래서 FastAPI에서 `422`가 보이면 "내 비즈니스 로직이 거절했다"보다 먼저 **요청이 서버에 어떤 모양으로 도착했는지**를 확인해야 합니다. 경위는 [Teammate 트러블슈팅](/projects/teammate#트러블슈팅)에, 왜 `uvicorn`만 설치하기로 했는지는 [기술 기록](/blog/uvicorn-422-empty-body)에 있습니다.

## 5. 502 vs 503 vs 504: 서버 오류의 세 얼굴

`500`은 **내 서버 안에서** 문제가 생긴 것입니다. `502`·`504`는 이름에 들어간 **Gateway**가 핵심입니다. 요청을 받은 서버(프록시, 로드 밸런서, API 게이트웨이)가 **뒤에 있는 서버에 일을 넘겼는데** 그쪽이 문제인 경우입니다.

| 코드 | 상황 | 비유 |
| --- | --- | --- |
| 502 Bad Gateway | 뒤의 서버가 **이상한 응답**을 줬다 (또는 연결이 끊겼다) | 전화를 걸었는데 알아들을 수 없는 소리가 났다 |
| 503 Service Unavailable | 서버가 **지금은** 일을 받을 수 없다 | "지금은 바빠서 못 받아요, 나중에 걸어 주세요" |
| 504 Gateway Timeout | 뒤의 서버가 **제때 답하지 않았다** | 전화를 걸었는데 아무도 안 받았다 |

`503`은 "일시적"이라는 점이 중요합니다. 서버는 `Retry-After` 헤더로 언제 다시 오면 되는지 알려 줄 수 있습니다. 점검이나 과부하처럼 **곧 나아질 상황**에 씁니다.

배포 직후 `502`가 보이면 애플리케이션이 아직 뜨지 않았거나 죽은 경우가 많고, `504`가 보이면 애플리케이션은 살아 있지만 **응답이 느린** 경우가 많습니다. 로그를 볼 위치가 달라집니다.

## 6. 어떤 코드를 고를까

API를 만들 때는 요청이 서버에서 검사받는 **순서대로** 물어보면 고르기 쉽습니다.

![누구인지, 권한, 대상, 형식, 상태 순서로 물어 401·403·404·400·409·2xx를 고르는 흐름](/images/posts/http-status-codes/03-decision-flow.svg)

1. 누구인지 확인됐나? 아니면 `401`.
2. 권한이 있나? 아니면 `403`. 존재를 숨겨야 하면 `404`.
3. 대상이 있나? 아니면 `404`.
4. 요청 형식과 값이 맞나? 아니면 `400` (팀 규칙에 따라 `422`).
5. 지금 상태에서 할 수 있나? 아니면 `409`.
6. 모두 통과했다면 성공. 새로 만들었으면 `201`, 돌려줄 본문이 없으면 `204`, 그 밖에는 `200`.

실제 프레임워크에서는 형식 검증이 인증보다 먼저 돌 때도 있어서, 이 순서가 언제나 정확하지는 않습니다. 하지만 **"무엇을 실패했는가"를 묻는 틀**로는 충분합니다.

성공 코드에도 RePlant 예가 있습니다. **알림 모두 읽음 처리**는 성공하면 본문 없이 `204`를 줍니다. 프론트는 "성공했다"만 알면 되고, 돌려줄 데이터가 없기 때문입니다.

### 한 API에서 코드를 나눠 쓴 예: 모의 택배사 예약 API

RePlant에서 만든 모의 택배사 서버([404-express](/projects/404-express))의 택배 예약 API는 **멱등키**를 받습니다. 멱등키는 "이 요청은 앞의 그 요청과 같은 요청이다"를 알려 주는 값입니다. 네트워크가 끊겨 클라이언트가 같은 예약을 다시 보내도, 택배가 두 번 예약되지 않게 해 줍니다.

| 상황 | 응답 | 이유 |
| --- | --- | --- |
| 처음 예약 | `201` | 새 예약(송장)을 만들었다 |
| 같은 멱등키 + 같은 본문을 다시 요청 | `200` (같은 송장) | 새로 만든 게 없으니 201이 아니다. 앞의 결과를 그대로 돌려준다 |
| 같은 멱등키 + 다른 본문 | `409 IDEMPOTENCY_KEY_REUSED` | 이미 다른 요청에 쓴 키와 부딪힌다 |
| 멱등키 형식이 틀림 | `400` | 요청 자체가 잘못됐다 |
| API 키가 틀림 | `401` | 누가 보냈는지 확인하지 못했다 |

같은 "예약" API 하나에서 `201`·`200`·`409`·`400`·`401`이 모두 나옵니다. 각 코드가 **무엇이 일어났는지**를 정확히 말해 주기 때문에, 클라이언트는 코드만 보고 다음 행동을 정할 수 있습니다.

## 7. 다시 시도할까 말까: 상태 코드와 재시도

상태 코드를 정확히 골라야 하는 가장 실용적인 이유는 **재시도**입니다. 클라이언트는 보통 상태 코드를 보고 다시 보낼지 정합니다.

| 응답 | 보통 다시 시도하나 | 이유 |
| --- | --- | --- |
| 5xx (`500`, `502`, `503`, `504`) | 한다 | 서버 쪽 일시적인 문제일 수 있다. 시간이 지나면 나아질 수 있다 |
| `408 Request Timeout` | 한다 | 요청이 늦게 도착했을 뿐, 요청 내용은 문제가 아닐 수 있다 |
| `429 Too Many Requests` | 한다 (기다렸다가) | 너무 자주 보낸 것이니, 쉬었다 보내면 된다. `Retry-After`가 있으면 따른다 |
| 그 밖의 4xx (`400`, `401`, `403`, `404`, `409`, `422`) | 안 한다 | **요청이 그대로면 결과도 그대로다.** 요청을 고쳐야 한다 |

4xx를 다시 보내지 않는 이유는 간단합니다. 형식이 틀린 요청은 열 번 보내도 형식이 틀립니다. 다시 보내 봐야 서버 부담만 늘어납니다. 5xx라도 `501 Not Implemented`처럼 "그 기능 자체가 없다"는 코드는 다시 보내도 소용이 없으니 예외입니다.

다시 시도할 때는 두 가지를 같이 챙겨야 합니다.

- **간격 늘리기**: 바로 연달아 보내지 않고, 기다리는 시간을 점점 늘린다. 장애 난 서버에 요청이 몰리는 걸 막는다.
- **멱등성**: `GET`·`PUT`·`DELETE`는 규격상 여러 번 보내도 결과가 같은 **멱등 메서드**라 다시 보내기 쉽습니다. `POST`는 그렇지 않아서, 다시 보내도 안전하려면 앞의 **멱등키** 같은 장치가 필요합니다.

### RePlant 택배사 클라이언트: 실패를 두 종류로 나누기

RePlant의 택배사 클라이언트는 실패를 이렇게 나눴습니다.

- **다시 시도할 수 있는 실패**: 5xx, `408`, `429`, 연결 실패
- **다시 시도하지 않는 실패**: 그 밖의 4xx

위 표를 그대로 코드로 옮긴 것입니다.

### 반대 방향: 웹훅을 받을 때는 200을 고른 이유

이번에는 RePlant가 **받는 쪽**입니다. 택배사는 웹훅을 보낼 때 **5xx를 받으면 다시 보내고, 4xx를 받으면 포기**하는 규칙을 씁니다.

그런데 웹훅에는 이상한 이벤트도 섞여 옵니다.

- 이미 받은 이벤트가 **중복**으로 온다.
- 이벤트 **순서가 뒤바뀌어** 온다.
- RePlant가 **모르는 주문번호**의 이벤트가 온다.

이런 이벤트에 5xx를 주면 어떻게 될까요? 택배사는 다시 보냅니다. 하지만 **다시 보내도 결과는 같습니다.** 중복은 계속 중복이고, 모르는 주문번호는 계속 모릅니다. 그러면 재전송이 끝없이 이어지고, 그 뒤에 와야 할 **다음 이벤트까지 막힙니다.**

그래서 RePlant는 이런 경우 **`200`으로 답했습니다.** "잘 받았다, 다시 보내지 않아도 된다"는 뜻입니다. 처리할 수 없는 이벤트는 서버 쪽에서 따로 기록해 두면 됩니다.

> 상태 코드는 "무슨 일이 있었나"를 알리는 동시에, **상대에게 다음 행동을 지시하는 신호**이기도 합니다. 상대가 그 코드를 받고 무엇을 할지까지 생각하고 골라야 합니다.

## 헷갈릴 때 외우는 법

- **첫 자리부터.** 2는 됐다, 4는 너 때문, 5는 나 때문.
- **401은 "누구세요?", 403은 "안 돼요", 404는 "없어요".** 401의 이름 Unauthorized에 속지 말자. 인증 실패다.
- **남의 것을 물으면 404.** 있는지조차 말해 주지 않는 것도 답이다.
- **400은 요청이 틀렸고, 409는 타이밍이 틀렸다.** 상태가 바뀌면 성공할 요청이면 409.
- **502는 이상한 답, 503은 지금 바쁨, 504는 답이 없음.**
- **201은 새로 만들었을 때만, 204는 본문이 없을 때만.**
- **다시 보낼 건 5xx·408·429뿐.** 4xx는 요청을 고쳐서 보낸다.
