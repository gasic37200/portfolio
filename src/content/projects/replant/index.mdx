## 문제와 해결 방향

> **문제:** 결제가 끝난 주문을 실제 택배 흐름에 연결해야 하는데, 외부 택배사 API는 느리거나 실패할 수 있고 상태 알림(웹훅)은 순서와 횟수가 보장되지 않는다.
>
> **해결:** 결제와 택배 예약을 트랜잭션으로 분리하고 멱등키로 재시도하며, 웹훅은 앞으로만 반영해 어떤 순서로 와도 상태가 일관되게 한다.

## 내 역할과 핵심 기여

- **배송 모듈** — 결제 후 배송 생성과 택배사 예약 연동(#103), 결제 커밋 후 예약 분리(#129), 미예약 건 재예약 스케줄러(#149), 배송 취소와 택배사 예약 취소 연동(#168)
- **웹훅 수신** — API 키 검증, 상태 단방향 진행, 중복·역순 무시(#123), 수거 시 택배비 정산 이벤트(#151)
- **알림 모듈** — 알림 저장·조회 API와 배송 알림(#176), SSE 실시간 전달(#177)
- **모의 택배사** — 실제 택배사 대신 호출할 [404-express](/projects/404-express)를 따로 개발
- **팀 인프라** — 운영 Dockerfile·compose와 배포 스크립트(#165, #185), 운영 Redis 구성(#10), PR CI 워크플로(#35)

회원, 상품, 장바구니·주문, 결제·정산은 다른 팀원이 담당했습니다.

## 아키텍처

**결제 완료 → 배송 생성(READY) 커밋 → 택배사 예약 → 웹훅으로 상태 반영 → 알림(SSE)**

- Spring Modulith로 도메인별 모듈을 나누고, 수거 완료 시 택배비 정산은 이벤트로 정산 모듈에 전달
- 택배사 예약은 결제 트랜잭션 밖에서 멱등키(`courierOrderNo`)로 호출해, 재시도해도 송장이 하나만 생기게 함
- 배송 상태가 바뀌면 알림을 저장하고 SSE로 실시간 전달

## 주요 구현

1. **멱등 예약과 재예약** — 배송 생성 시 멱등키를 함께 저장하고, 예약에 실패한 READY 건은 5분마다 같은 키로 재예약
2. **경합 처리** — 예약과 취소가 겹칠 때 낙관적 락 충돌을 처리하고, 택배사 취소 실패는 재시도
3. **웹훅 수신 규칙** — API 키 검증 후 상태는 앞으로만 진행, 중복·역순은 200으로 무시
4. **실시간 알림** — 배송 단계별로 구매자·판매자에게 알림 저장 후 SSE 전달, 운영 Nginx에 SSE 전용 설정

## AI 활용

팀 프로젝트 전체를 Claude Code와 함께 진행했고, **한 세션이 한 가지 일에만 집중하도록** 작업 방식을 설계했습니다.

### 역할별 세션 분리

| 세션 | 담당 |
| --- | --- |
| 워크용 | 기능 코드, API, 테스트 |
| 인프라용 | AWS, Docker, Kafka, Redis, 배포, 환경변수 |
| 기획용 | 저장소 docs의 기획 문서 |
| 정리용 | 노션·ERD 정리, 의사결정 기록, PR·세션 요약 (저장소는 수정하지 않음) |
| 리뷰용 | AI 리뷰 결과 정리 (수정은 워크용으로 넘김) |
| 프론트용 | 디자인 수정 |

같은 폴더를 쓰는 세션끼리는 같은 파일을 동시에 고치지 않는 규칙을 두었습니다.

### 컨텍스트를 아끼는 방법

- **요약만 넘기기** — 직접 만든 `send-to` 스킬로, 대화 주제가 다른 세션 담당이면 맥락을 요약해 그 세션으로 보냅니다. 대화 전체를 옮기지 않습니다.
- **결정을 파일로 고정** — "ElastiCache를 쓰지 않는다", "무료배송 정책은 없다" 같은 결정은 메모리 파일과 docs에 한 번만 적어, 세션마다 다시 설명하지 않게 했습니다.
- **반복 작업은 스킬로** — 이슈의 다음 할 일을 체크리스트에서 뽑아 주는 스킬 등으로 같은 지시를 반복하지 않았습니다.

### 프롬프트 패턴

1. **역할과 범위를 먼저 정한다** — "넌 이제부터 일단커밋의 인프라 전용 에이전트야"
2. **참고할 자료를 가리킨다** — "25~28페이지를 참고해."
3. **보존 조건을 건다** — "기존꺼는 냅두고 아래쪽에 넣어줘"
4. **AI의 설명을 되묻는다** — "트랜잭션 분리한거 아니야?"

### AI가 틀린 것을 바로잡은 사례

- AI가 Redis를 ElastiCache로 옮기자고 제안 → EC2 위 Docker Redis로 확정하고, 같은 제안을 반복하지 않도록 메모리에 기록
- AI가 배송비 0원 대비 방어 코드를 넣으려 함 → 무료배송 정책이 없으므로 불필요하다고 정정
- "트랜잭션을 분리했는데 왜 응답이 늦지?"를 되물어, **트랜잭션 분리와 비동기 처리는 다르다**는 점(같은 요청 스레드에서 호출하면 여전히 기다린다)을 짚어냄 → [기술 기록](/blog/payment-commit-then-courier)

## 회고

외부 시스템과 연동하는 기능은 "성공했을 때"보다 **느릴 때, 실패할 때, 순서가 꼬일 때**를 먼저 설계해야 한다는 것을 배웠습니다. 멱등키, 재시도, 단방향 상태 전이로 대부분을 막았지만, 택배사 응답 대기와 상태 대사(직접 조회해 맞추기)는 다음 개선 과제로 남겼습니다. 또 실제 택배사 대신 쓸 모의 택배사를 직접 만들면서, 호출하는 쪽과 받는 쪽의 규칙(멱등키, 재전송, 응답 형식)을 양쪽에서 함께 맞춰 볼 수 있었습니다.
