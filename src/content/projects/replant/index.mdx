## 문제와 해결 방향

> **문제:** 결제가 끝난 주문을 실제 택배 흐름에 연결해야 하는데, 외부 택배사 API는 느리거나 실패할 수 있고 상태 알림(웹훅)은 순서와 횟수가 보장되지 않는다.
>
> **해결:** 결제와 택배 예약을 트랜잭션으로 분리하고 멱등키로 재시도하며, 웹훅은 앞으로만 반영해 어떤 순서로 와도 상태가 일관되게 한다.

## 주요 구현

![배송·알림 상태 흐름과 외부 연동](/images/projects/replant/shipment-flow.webp)

1. **멱등 예약과 재예약** — 배송 생성 시 멱등키를 함께 저장하고, 예약에 실패한 READY 건은 5분마다 같은 키로 재예약
2. **경합 처리** — 재예약과 취소가 겹칠 때 `@Version` 낙관적 락으로 늦게 저장하는 쪽을 실패시키고, 택배사 취소 실패는 재시도
3. **웹훅 수신 규칙** — API 키 검증 후 상태는 앞으로만 진행, 중복·역순은 200으로 무시
4. **실시간 알림** — Kafka 이벤트는 이벤트 키 UNIQUE로 중복을 막고, 상대가 한 일만 알림. SSE로는 신호만 보내 화면이 다시 조회하게 하고, 운영 Nginx에 SSE 전용 설정

<details>
<summary><strong>담당 API 명세 보기</strong></summary>

**알림** — 모두 로그인(JWT) 필요

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/v1/notifications` | 내 알림 목록 (`isRead`, `page`, `size`) |
| GET | `/api/v1/notifications/subscribe` | SSE 구독. `unread` 이벤트로 안 읽은 수 전달, 30초마다 ping, `X-Accel-Buffering: no` |
| GET | `/api/v1/notifications/unread-count` | 안 읽은 알림 수 |
| PATCH | `/api/v1/notifications/{id}` | 한 건 읽음 처리 (`{ "isRead": true }`) |
| PATCH | `/api/v1/notifications` | 전체 읽음 처리, 204 |

남의 알림 id로 요청해도 `NOTIFICATION_NOT_FOUND`(404)를 돌려줘, 알림이 있는지 자체를 알려 주지 않습니다. `isRead=false`는 `ONLY_READ_SUPPORTED`(400)입니다.

**택배사 웹훅**

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/api/v1/webhooks/courier` | 택배사 상태 변경 수신. JWT 대신 `X-Api-Key`를 상수 시간 비교로 검증, 틀리면 401 |

요청은 `eventId`, `courierOrderNo`, `trackingNo`, `status`(PICKED_UP / IN_TRANSIT / DELIVERED), `occurredAt`입니다. 중복·역순·모르는 주문번호도 200으로 답해 택배사가 다시 보내지 않게 하고, 로그만 남깁니다.

**배송** — 배송 전용 공개 API는 없고, 배송 상태와 단계별 시각은 주문 상세·판매 주문 상세에 함께 내려갑니다. 수거 뒤 취소(`SHIPMENT_NOT_CANCELABLE`), 배송 완료 전 구매 확정(`SHIPMENT_NOT_DELIVERED`)은 409로 막습니다.

**상태값과 이벤트**

- 배송 상태: `READY → BOOKED → PICKED_UP → IN_TRANSIT → DELIVERED`, 취소 시 `CANCELLED`
- 배송이 발행하는 Kafka 토픽: `market.shipment-status-changed.v1`, `market.shipment-picked-up.v1`(정산이 구독)
- 알림 모듈은 배송 상태 변경과 주문 쪽 토픽(결제, 취소, 구매 확정, 자동 구매 확정) 5개를 구독해 판매자·구매자 알림 12종을 만듭니다

모의 택배사 쪽 API(예약·조회·취소, 관리자용 강제 진행·웹훅 재전송)는 [404-express](/projects/404-express)에 정리했습니다.

## 인프라

EC2 한 대(t3.medium)에 백엔드·DB·Redis·Kafka와 모의 택배사를 Docker Compose로 올리고, 외부에는 Nginx의 80/443만 열었습니다.

| 구성 | 실행 방식 | 메모리 |
| --- | --- | --- |
| Spring 앱 | 컨테이너 (멀티스테이지 빌드, root가 아닌 사용자로 실행) | 1GB |
| PostgreSQL 17 | 컨테이너 | 512MB |
| Redis 8 | 컨테이너 | maxmemory 256MB |
| Kafka 4.2 (KRaft 단일 노드) | 컨테이너 | 768MB |
| 404-express | 별도 저장소의 별도 compose | 128MB |
| Nginx | 호스트에 설치, HTTPS 종단 | — |
| 프론트 | 일회용 Node 컨테이너로 빌드해 정적 파일로 배치 | — |

운영 구성을 로컬에서 그대로 띄워 보니 실제 사용량은 앱 약 520MB, Kafka 약 400MB, PostgreSQL 약 55MB로 상한 안에 들어왔습니다. 앱 이미지는 JDK로 빌드하고 JRE로 실행하도록 단계를 나눴고 715MB입니다.

- **모의 택배사 분리** — 404-express는 저장소와 compose가 따로라 배포 주기가 다릅니다. 외부 Docker 네트워크 `replant-net`을 한 번 만들어 두 compose가 함께 쓰고, 별칭(`replant-app`, `404-express`)으로 서로 호출합니다. 택배사는 포트를 하나도 열지 않아 같은 서버 안에서만 통신하고, 양쪽 `X-Api-Key`는 배포 스크립트가 같은 값으로 맞춥니다.
- **포트 노출 최소화** — 앱·DB·Redis 포트는 모두 `127.0.0.1`에만 바인딩하고, DB는 SSH 터널로만 접속합니다. SSH는 본인 IP만 허용했습니다.
- **Redis** — `requirepass`, `maxmemory 256mb`, `noeviction`, `appendonly yes`. 인증번호·토큰·멱등키를 담는 임시 저장소라 메모리가 차도 키를 지우지 않게 하고, 그 대신 모든 키에 TTL을 겁니다.
- **Nginx** — Let's Encrypt 인증서(Certbot 자동 갱신), HTTP는 HTTPS로 리다이렉트, `/api`·OAuth 경로는 앱으로 프록시하고 나머지는 SPA로 응답합니다. SSE 경로만 따로 떼어 `proxy_buffering off`, `proxy_read_timeout 1h`를 주고, 앱도 `X-Accel-Buffering: no`와 30초 ping을 보냅니다([#209](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/209)).
- **배포** — 서버에서 `deploy.sh` 한 번으로 실행합니다([#165](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/165), [#185](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/185)). 비밀값 확인 → 기존 컨테이너 내림(볼륨 유지) → BE·택배사·FE 최신 코드 받기 → `.env.example` 대비 빠진 환경변수 검사 → 프론트 번들에 결제 키가 들어갔는지 검사 → Nginx 설정 재작성 → 기동 후 health 대기. 비밀값 원본은 서버의 권한 600 파일 하나에만 두고, S3는 EC2 IAM 역할로 접근해 AWS 키를 두지 않았습니다.
- **S3 이미지** — 업로드는 서버가 발급한 10분짜리 Presigned PUT URL로 프론트가 S3에 직접 올리고, 조회는 공개 URL로 합니다. 버킷 정책(`products/*`, `species/*`만 공개 조회), EC2 IAM 역할(앱에 AWS 키 없음), CORS, 로컬 S3 환경(RustFS, [#126](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/126)), 품종 사진 888장 업로드를 맡았고, URL 발급 API는 팀원이 구현했습니다([#124](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/124)).
- **CI** — PR마다 GitHub Actions로 빌드를 돌리고([#35](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/35)), develop에는 빌드 통과를 예외 없는 필수 규칙으로 걸었습니다. CD는 아직 없고 배포는 수동입니다.

**인프라**

공통 배경은 교육 과정 AWS 계정 규칙입니다. 처음 버전 개발 기간에는 EC2 1대만 쓸 수 있고, RDS·ElastiCache·ACM 같은 관리형 서비스는 따로 문의해야 하며, 운영진 방침도 "관리형 대신 직접 구성"이었습니다.

| 고른 것 | 다른 선택지 | 이유 |
| --- | --- | --- |
| Docker Compose | Kubernetes, ECS | EC2 1대 제한, ECS는 허용 목록 밖. 대신 단일 장애점이고 무중단 배포가 없음 |
| PostgreSQL·Redis 컨테이너 | RDS, ElastiCache | 관리형은 문의 대상이고 직접 구성 방침. 보안·메모리·영속성 설정을 직접 정함. 대신 백업과 장애 대응을 직접 책임짐 |
| Kafka KRaft 단일 노드 | ZooKeeper 구성, 다중 브로커, MSK | 팀 규칙상 비동기 이벤트는 Kafka, KRaft라 ZooKeeper 불필요, 서버가 1대. 대신 복제가 1이라 장애 시 유실 가능 |
| Let's Encrypt + 무료 도메인 | ACM + ALB | ACM은 문의 대상이고 ALB가 필요. 인증서는 Certbot이 자동 갱신 |
| 서버에서 직접 이미지 빌드 | GHCR, ECR | 첫 배포를 `deploy.sh` 하나로 빠르게 끝내려고. 대신 첫 빌드가 10분 넘게 걸리고 CPU 크레딧을 소진함(Kafka 헬스체크 장애의 원인) |
| S3 업로드는 Presigned PUT URL, 조회는 공개 URL | 서버 경유 업로드, 비공개 버킷 + Presigned GET | 업로드가 서버를 거치지 않아 EC2 메모리·대역폭 부담이 없고, 쓰기 권한은 형식·크기까지 서명한 10분짜리 URL로만 줌. 상품 사진은 누구나 보는 이미지라 조회는 서명 없이 공개 |
| 로컬 S3로 RustFS 컨테이너 ([#126](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/126)) | MinIO, 개발용 실제 S3 버킷 | AWS 계정 없이 팀원 누구나 docker compose로 같은 S3 환경을 띄움. 초기화 컨테이너가 버킷·공개 정책(`products/*`, `species/*`)·CORS를 운영과 같은 파일로 적용하고, 여러 번 실행해도 결과가 같음. MinIO는 공식 Docker 이미지를 받을 수 없어 대체. 로컬은 endpoint `localhost:9000` + path-style, 운영은 EC2 IAM 역할 |
| GitHub Actions CI | — | 무료이고 저장소에 내장. develop 규칙에 빌드 통과를 예외 없는 필수 체크로 지정 |

## 회고

외부 시스템과 연동하는 기능은 정상 흐름보다 **실패했을 때 누가 다시 보낼지**를 먼저 설계해야 한다는 것을 체감했습니다. 멱등키, 재시도, 단방향 상태 전이, 낙관적 락으로 대부분을 막았지만, 택배사 응답 대기와 상태 대사(직접 조회해 맞추기)는 남은 과제입니다. 또 모의 택배사를 직접 만들면서 외부 연동 계약(응답 코드, 재시도 규칙)을 호출하는 쪽과 받는 쪽 양쪽에서 이해할 수 있었습니다.

운영에서는 #176 이후 추가한 알림 종류 7개(#188에서 4개, #193에서 3개)가 저장되지 않는 일도 겪었습니다. Hibernate가 `@Enumerated(STRING)` 컬럼에 허용 값을 체크 제약으로 만드는데, 테스트는 `ddl-auto: create-drop`이라 매번 최신 값으로 만들고 운영은 `update`라 기존 제약을 고치지 않았습니다. CI가 운영과 다른 스키마를 검사하고 있었던 것이고, 운영 DB에서 제약을 직접 지워 해결했습니다. 처음 버전에서 Flyway를 끈 결정의 대가였습니다.

팀장으로서 협업 규칙, CI, 문서를 정형화해 협업 기반을 만드는 건 처음이라 미숙했지만, 큰 도움이 된 경험이었습니다. 자체 평가는 8/10입니다. 남은 과제는 [추가한 기능과 개선한 점](#추가한-기능과-개선한-점)에 모아 두었습니다.
