## 문제와 해결 방향

> **문제:** 결제가 끝난 주문을 실제 택배 흐름에 연결해야 하는데, 외부 택배사 API는 느리거나 실패할 수 있고 상태 알림(웹훅)은 순서와 횟수가 보장되지 않는다.
>
> **해결:** 결제와 택배 예약을 트랜잭션으로 분리하고 멱등키로 재시도하며, 웹훅은 앞으로만 반영해 어떤 순서로 와도 상태가 일관되게 한다.

## 내 역할과 핵심 기여

- **배송 모듈** — 결제 후 배송 생성과 택배사 예약 연동(#103), 결제 커밋 후 예약 분리(#129), 미예약 건 재예약 스케줄러(#149), 배송 취소와 택배사 예약 취소 연동(#168)
- **웹훅 수신** — API 키 검증, 상태 단방향 진행, 중복·역순 무시(#123), 수거 시 택배비 정산 이벤트(#151)
- **알림 모듈** — 알림 저장·조회 API와 배송 알림(#176), SSE 실시간 전달(#177)
- **모의 택배사** — 실제 택배사 API로는 테스트할 수 없어 당근 택배 같은 전용 택배사를 제안하고 [404-express](/projects/404-express)로 직접 개발. 단위 테스트에서는 멘토님이 추천한 WireMock으로 택배사 응답을 흉내 냄(#103, #168)
- **팀 인프라** — 운영 Dockerfile·compose와 배포 스크립트(#165, #185), 운영 Redis 구성(#10), PR CI 워크플로(#35)
- **팀장** — 이슈 1개 = PR 1개, 리뷰 승인 후 머지 같은 협업 규칙과 CI, 문서를 정리

회원, 상품, 장바구니·주문, 결제·정산은 다른 팀원이 담당했습니다.

## 아키텍처

![RePlant 서비스 아키텍처](/images/projects/replant/architecture.webp)

**결제 완료 → 배송 생성(READY) 커밋 → 택배사 예약 → 웹훅으로 상태 반영 → 알림(SSE)**

- Spring Modulith로 member·product·market·payment·settlement·notification 모듈을 나누고, 모듈 간에는 공개 Query·UseCase·이벤트로만 호출
- 배송은 상태만 바꾸고, 배송비·알림·구매 확정은 이벤트(Kafka)로 각 모듈이 처리
- 택배사 예약은 결제 트랜잭션 밖에서 멱등키(`courierOrderNo`)로 호출해, 재시도해도 송장이 하나만 생기게 함
- 배송 상태가 바뀌면 알림을 저장하고 SSE로 실시간 전달

## 주요 구현

![배송·알림 상태 흐름과 외부 연동](/images/projects/replant/shipment-flow.webp)

1. **멱등 예약과 재예약** — 배송 생성 시 멱등키를 함께 저장하고, 예약에 실패한 READY 건은 5분마다 같은 키로 재예약
2. **경합 처리** — 재예약과 취소가 겹칠 때 `@Version` 낙관적 락으로 늦게 저장하는 쪽을 실패시키고, 택배사 취소 실패는 재시도
3. **웹훅 수신 규칙** — API 키 검증 후 상태는 앞으로만 진행, 중복·역순은 200으로 무시
4. **실시간 알림** — Kafka 이벤트는 이벤트 키 UNIQUE로 중복을 막고, 상대가 한 일만 알림. SSE로는 신호만 보내 화면이 다시 조회하게 하고, 운영 Nginx에 SSE 전용 설정

<details>
<summary><strong>담당 API 명세 보기</strong></summary>

**알림** — 모두 로그인(JWT) 필요

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/v1/notifications` | 내 알림 목록 (`isRead`, `page`, `size`) |
| GET | `/api/v1/notifications/subscribe` | SSE 구독. `unread` 이벤트로 안 읽은 수 전달, 30초마다 ping, `X-Accel-Buffering: no` |
| GET | `/api/v1/notifications/unread-count` | 안 읽은 알림 수 |
| PATCH | `/api/v1/notifications/{id}` | 한 건 읽음 처리 (`{ "isRead": true }`) |
| PATCH | `/api/v1/notifications` | 전체 읽음 처리, 204 |

남의 알림 id로 요청해도 `NOTIFICATION_NOT_FOUND`(404)를 돌려줘, 알림이 있는지 자체를 알려 주지 않습니다. `isRead=false`는 `ONLY_READ_SUPPORTED`(400)입니다.

**택배사 웹훅**

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/api/v1/webhooks/courier` | 택배사 상태 변경 수신. JWT 대신 `X-Api-Key`를 상수 시간 비교로 검증, 틀리면 401 |

요청은 `eventId`, `courierOrderNo`, `trackingNo`, `status`(PICKED_UP / IN_TRANSIT / DELIVERED), `occurredAt`입니다. 중복·역순·모르는 주문번호도 200으로 답해 택배사가 다시 보내지 않게 하고, 로그만 남깁니다.

**배송** — 배송 전용 공개 API는 없고, 배송 상태와 단계별 시각은 주문 상세·판매 주문 상세에 함께 내려갑니다. 수거 뒤 취소(`SHIPMENT_NOT_CANCELABLE`), 배송 완료 전 구매 확정(`SHIPMENT_NOT_DELIVERED`)은 409로 막습니다.

**상태값과 이벤트**

- 배송 상태: `READY → BOOKED → PICKED_UP → IN_TRANSIT → DELIVERED`, 취소 시 `CANCELLED`
- 배송이 발행하는 Kafka 토픽: `market.shipment-status-changed.v1`, `market.shipment-picked-up.v1`(정산이 구독)
- 알림 모듈은 배송 상태 변경과 주문 쪽 토픽(결제, 취소, 구매 확정, 자동 구매 확정) 5개를 구독해 판매자·구매자 알림 12종을 만듭니다

모의 택배사 쪽 API(예약·조회·취소, 관리자용 강제 진행·웹훅 재전송)는 [404-express](/projects/404-express)에 정리했습니다.

| Redis는 `noeviction`, 모든 키에 TTL, 키는 `도메인:용도:식별자` | 캐시가 아니라 인증번호·토큰·멱등키 임시 저장소라, 메모리가 찼을 때 몰래 지워지면 조용한 버그가 됨 |
| Redis 외부 차단을 세 겹으로 (127.0.0.1 바인딩, 보안 그룹 미개방, 비밀번호) | 서버가 1대라 프라이빗 서브넷으로 나눌 대상이 없어, 한 겹이 뚫려도 나머지가 막게 함 |
| 퍼블릭 서브넷 1개, NAT 없음, t3.medium | 서버 1대에서는 분리 이득보다 NAT 비용이 큼. Spring·PostgreSQL·Redis·Kafka를 한 서버에 띄우면 2GB는 부족 |
| 탄력적 IP와 재시작에 강한 구성 (Docker 자동 시작, `restart: unless-stopped`, Redis appendonly) | 서버가 매일 18시에 꺼지고 09시에 켜져 공인 IP와 컨테이너 상태가 흔들림 |
| 코드 패키지명은 `justcommit` 유지, 컨테이너·DB·앱 이름만 `replant` | 패키지명을 바꾸면 팀원 브랜치 전체와 충돌 |
| develop 보호 규칙과 CI 규칙을 분리 | 관리자 예외가 규칙 묶음 전체를 건너뛰므로, 직접 머지할 때도 CI는 반드시 돌게 하려고 |
| API 경로를 행위가 아닌 자원 중심으로 수정 | 멘토링에서 RESTful하지 않다는 지적 |
| 택배사 재시도는 별도 API 대신 멱등 설계로 처리 | 멘토링 반영 |
| 택배 예약을 결제 커밋 뒤로 분리 (#129) | 결제가 롤백돼도 택배 예약이 남는 문제. 남은 한계는 응답 지연 |
| 웹훅 중복은 eventId 테이블 대신 상태 순서로 거름 | 상태가 한 방향으로만 가서 같은 상태가 다시 오는 건 모두 재전송. eventId는 로그 추적용 |
| 운영 DB는 Flyway 대신 `ddl-auto: update`, Flyway는 최종 프로젝트로 | 마이그레이션 파일이 없어 `validate`로는 빈 DB에서 기동 실패. 대가로 NOT NULL 컬럼 추가가 조용히 실패해 정산이 누락되는 일을 겪음 |
| 배송비 0원 방어 코드를 넣지 않음 | 무료배송 정책이 없어 배송비는 항상 0보다 큼 |
| 수거 시점에 배송비 정산 이벤트 발행 (#151) | 수거 전까지만 취소할 수 있으므로 수거가 배송비 확정 시점 |
| 알림은 Spring 이벤트 대신 Kafka로 받고 SSE로는 신호만 | 팀이 모듈 간 통신을 Kafka로 통일했고, 원본을 DB에 두면 SSE가 끊겨도 다시 맞출 수 있음 |
| 구매자가 직접 취소한 주문은 구매자에게 알리지 않음 (#212) | 상대가 한 일만 알림 |

**팀 규칙** — develop 기본 브랜치, squash 머지만 허용, 승인 1명과 CI(`./gradlew build`) 통과 필수. 커밋·PR 제목은 `Feat: [모듈] 내용 (#이슈)`. 다른 모듈의 Repository·Entity는 직접 참조하지 않고 공개 API·DTO와 ID로만 참조하며, 비동기 이벤트는 Kafka로만 처리합니다.

## AI 활용

팀 프로젝트 전체를 Claude Code와 함께 진행했고, **한 세션이 한 가지 일에만 집중하도록** 역할별로 세션을 나눠 썼습니다.

| 세션 | 담당 |
| --- | --- |
| 워크용 | 기능 코드, API, 테스트 |
| 인프라용 | AWS, Docker, Kafka, Redis, 배포, 환경변수 |
| 기획용 | 저장소 docs의 기획 문서 |
| 정리용 | 노션·ERD 정리, 의사결정 기록, PR·세션 요약 (저장소는 수정하지 않음) |
| 리뷰용 | AI 리뷰 결과 정리 (수정은 워크용으로 넘김) |
| 프론트용 | 디자인 수정 |

대화 주제가 다른 세션 담당이면, 직접 만든 `send-to` 스킬이 대화를 분석해 그 세션으로 일을 넘겼습니다.

## 회고

외부 시스템과 연동하는 기능은 정상 흐름보다 **실패했을 때 누가 다시 보낼지**를 먼저 설계해야 한다는 것을 체감했습니다. 멱등키, 재시도, 단방향 상태 전이, 낙관적 락으로 대부분을 막았지만, 택배사 응답 대기와 상태 대사(직접 조회해 맞추기)는 남은 과제입니다. 또 모의 택배사를 직접 만들면서 외부 연동 계약(응답 코드, 재시도 규칙)을 호출하는 쪽과 받는 쪽 양쪽에서 이해할 수 있었습니다.

팀장으로서 협업 규칙, CI, 문서를 정형화해 협업 기반을 만드는 건 처음이라 미숙했지만, 큰 도움이 된 경험이었습니다. 자체 평가는 8/10입니다.

**다음 개선 방향**

- 택배 예약을 비동기로 바꾸고 서킷 브레이커로 택배사 장애를 격리
- 택배사 상태를 직접 조회하는 대사로 웹훅 유실 보완
- Spring Modulith 이벤트 발행 기록과 `@Externalized`로 Kafka 전송 유실 방지
