## 문제와 해결 방향

> **문제:** RePlant의 배송 기능에는 택배사가 필요한데, 실제 택배사 API로는 실패·재전송·웹훅 같은 상황을 만들어 테스트할 수 없다.
>
> **해결:** 당근 택배처럼 플랫폼 전용 택배사를 만들어, 멱등 예약·시간 기반 상태 진행·웹훅 재전송을 갖추고 서버가 꺼져도 이벤트가 유실되지 않게 한다.

## 내 역할과 핵심 기여

- **제안과 콘셉트** — 실제 택배사 API로는 원하는 상황을 테스트할 수 없어 당근 택배 같은 플랫폼 전용 택배사를 제안. 상태 흐름(예약 → 접수 → 배송 중 → 배송 완료)과 취소 규칙(수거 전에만, 배송 건 전체만. 부분 취소는 서버 내부 처리)을 결정([03c1a12](https://github.com/gasic37200/404-express/commit/03c1a12))
- **계약 설계** — 멱등키 `shipment-yyyyMMdd-NNNNNN`을 서버가 만들어 `Idempotency-Key` 헤더로 보내고 URL에는 송장번호만 쓰는 방식, 응답 형식을 팀 Spring 서버의 `ApiResponse`에 맞춰 서버 쪽 클라이언트가 같은 DTO로 파싱하게 함
- **유실 방지 구조 결정** — 웹훅을 기본으로 하되 DB outbox와 재전송, 서버 polling 대사로 보완
- **재전송 규칙 조정** — RePlant 수신부 규칙(중복·역순에 200, 상태는 앞으로만 반영)에 맞춰 4xx는 재전송하지 않고, 배송 건별 FIFO를 이벤트별 독립 재전송으로 변경([770b02e](https://github.com/gasic37200/404-express/commit/770b02e))
- **검증 기준 제시** — 기능마다 "확인 방법"을 함께 줘, 취소 점검에서 예약 → 즉시 취소 → 3분 20초 대기로 수거 웹훅 0건을 확인([46a3296](https://github.com/gasic37200/404-express/commit/46a3296))

서버 쪽 택배사 클라이언트와 웹훅 수신은 [RePlant](/projects/replant)의 배송 모듈에서 따로 구현했습니다.

## 아키텍처

**예약(멱등) → 시간 기반 자동 진행 → 상태 변경을 outbox에 기록 → 웹훅 전송 → 실패 시 재전송 → 5번 실패하면 DEAD**

- 상태 전이와 웹훅 적재를 **한 트랜잭션**으로 묶어, 상태는 바뀌었는데 알림만 빠지는 일이 없게 함
- 자동 진행은 배송 건마다 타이머를 잡지 않고, 워커가 실행 시점에 상태를 다시 읽음
- 자동 진행 워커와 outbox 전송 워커가 한 프로세스에서 돌고, 데이터는 SQLite 파일 하나(`shipments`, `webhook_outbox`)
- 실패한 웹훅은 DEAD 목록(DB, 재시작해도 유지)으로 모으고 관리자 API로 수동 재전송

## 주요 구현

1. **멱등 예약** — 응답이 유실돼 서버가 같은 키로 다시 요청해도 송장이 하나만 생깁니다. 같은 키 + 같은 본문은 200(같은 송장), 다른 본문은 409, 키 형식 오류는 400으로 `shipments.test.ts` 15개가 고정합니다.
2. **시간 기반 상태 진행** — 수거 3분·배송 중 2분·배송 완료 2분 간격(`*_DELAY_SEC`)으로 자동 진행합니다. 워커가 실행 시점에 상태를 다시 읽어 취소된 건은 진행하지 않습니다.
3. **웹훅 outbox와 재전송** — 1분 → 5분 → 30분 → 2시간 → 6시간 간격으로 최대 5번 재전송하고, 4xx는 설정·데이터 문제라 다시 보내지 않습니다. 재전송은 처음 저장한 `eventId`·`occurredAt` 그대로 보내고, 모두 실패하면 `DEAD`로 남겨 관리자 API로 다시 보냅니다([770b02e](https://github.com/gasic37200/404-express/commit/770b02e)).
4. **운영 배포** — RePlant와 같은 EC2의 Docker 네트워크 `replant-net`에서만 접근하도록 포트를 열지 않는 compose 구성으로 배포했습니다([cc0f59b](https://github.com/gasic37200/404-express/commit/cc0f59b)).

## 테스트와 검증

PR 없이 `main`에 커밋해 커밋 기준으로 정리했습니다.

| 커밋 | 추가한 테스트 | 확인한 것 |
| --- | --- | --- |
| 멱등 예약·조회·인증 [03c1a12](https://github.com/gasic37200/404-express/commit/03c1a12) | `shipments.test.ts` 15개 | 처음 요청 201, 같은 키 + 같은 본문 200(같은 송장), 다른 본문 409, 키 형식 오류 400, 키 오류 401 |
| 웹훅 재전송 [770b02e](https://github.com/gasic37200/404-express/commit/770b02e) | `webhooks.test.ts` 13개 | 1분 → 5분 → 30분 → 2시간 → 6시간 간격, 4xx(400·401·404·408·429) 재전송 없음, 5번 모두 실패 시 `DEAD`와 관리자 재전송, 이벤트별 독립 전송 |
| 배송 취소 [46a3296](https://github.com/gasic37200/404-express/commit/46a3296) | `cancel.test.ts` 10개 | 상태별 응답, 취소 뒤 자동 진행·웹훅 중단, 취소·수거 동시 처리(두 순서 모두) |
| 전체 | 38개 통과 | `npm run typecheck` 오류 없음 |

로컬 E2E로도 확인했습니다.

- **재전송** — 간격을 `5,5,5,5,5`초로 줄이고 수신기를 끈 채 진행하자 `fetch failed` 경고 2번 뒤 3번째 시도에서 같은 `eventId`·`occurredAt`으로 200, `SENT`. 잘못된 `WEBHOOK_API_KEY`는 401 한 번 뒤 재전송 없이 `DEAD`(attempts=1)
- **운영 compose** — 임시 `replant-net`에 가짜 RePlant 컨테이너를 두고 띄워 `healthy`, 공개 포트 없음, 메모리 한도 128MB, `http://404-express:3000`으로 health 200·예약 201·진행 200, 웹훅 도착 200
- **RePlant 연동** — RePlant 쪽에서 404-express 컨테이너로 예약한 뒤 웹훅 3건을 받아 READY → DELIVERED까지 DB에 반영되는 것을 수동 E2E로 확인([RePlant #123](https://github.com/prgrms-be-adv-devcourse/beadv8_8_JustCommit_BE/issues/123))

## 기술 선택 이유

| 고른 것 | 다른 선택지 | 이유 |
| --- | --- | --- |
| 자체 모의 택배사(404-express) + WireMock | 실제 택배사 API | 실제 API로는 실패·재전송·웹훅 상황을 만들 수 없음. 멘토님이 추천한 WireMock은 RePlant 단위 테스트에서 택배사 응답(예약 201·500, 취소 200·404·409·500)별 클라이언트 처리 확인에 쓰고, 404-express는 로컬·운영에서 RePlant와 실제로 주고받는 택배사로 역할을 나눔 |
| RePlant와 같은 EC2, 별도 compose + `replant-net` | Vercel + SQLite, Oracle 단독 배포 | 기획 단계에서 AI가 서버리스에서는 SQLite 파일이 유지되지 않고 자동 진행·웹훅 재전송 같은 상시 작업을 돌릴 수 없다고 짚어 Vercel을 버림. Oracle 단독 배포 대신 같은 EC2(B안)로 바꿔 포트를 열지 않고 내부 네트워크로만 통신 |
| 웹훅 이벤트별 독립 재전송 | 배송 건별 FIFO(처음 구현) | RePlant 수신부가 중복·역순에 200을 주고 상태는 앞으로만 반영해 송신 쪽 순서 보장이 필요 없어짐. 앞 이벤트의 재전송이 뒤 이벤트를 막지 않음. 대신 서버는 순서가 뒤바뀐 이벤트를 받을 수 있음([770b02e](https://github.com/gasic37200/404-express/commit/770b02e)) |
| 4xx는 재전송하지 않음, 최대 5번 | 408·429 재전송, 10번 후 DEAD(처음 구현) | 4xx는 설정이나 데이터 문제라 다시 보내도 결과가 같음 |
| Node 내장 `node:sqlite` | better-sqlite3(처음 합의) | 네이티브 빌드를 피하려고 AI가 바꿈. 보고는 받았지만 명시적으로 승인하지 않은 채 남아 있음 |

## AI 활용

이 프로젝트는 **코드 전부를 AI가 작성**했습니다. 대신 무엇을 만들지, 어떤 규칙을 지킬지, 어떻게 확인할지는 직접 정했습니다.

### 1. 질문받으며 기획하기 (grill-me)

`/grill-me` 스킬로 AI가 결정할 것을 라운드별로 질문하고, 매 질문에 추천안을 붙이게 했습니다. 저는 결정만 답했습니다. 6라운드에 걸쳐 멱등키, 알림 방식, 배포 환경, 응답 형식, 재시도 정책을 확정한 뒤 "맞아 시작해줘."로 구현을 시작했습니다. → [기술 기록](/blog/grill-me-planning)

### 2. 프롬프트가 대화에서 명세서로

| 단계 | 프롬프트 (발췌) | 결과 |
| --- | --- | --- |
| 기획 시작 | "가짜 택배사 하나가 필요해 … 당근 택배를 모방해서 … 서버가 꺼져서 이벤트 유실이 되지 않게끔" | grill 질문 라운드 시작 |
| 결정 | "stripe처럼 헤더로 빼고 … courierOrderNo는 url에 붙이지마" | 헤더 멱등키 확정 |
| 문서 골격 | "agent.md는 없어?" | AGENTS.md, CLAUDE.md, 운영·미결 문서 작성 |
| 기능 명세 | "4xx 재전송하지 않음 / 연결 실패, 타임아웃(5초), 5xx: 재전송 / 1분 → 5분 → 30분 → 2시간 → 6시간 … 확인 방법: 서버를 끈 상태에서 배송을 진행 → 재전송 로그 확인" | 재전송 구현과 로컬 재현 |
| 검증 요청 | "다른 부분만 고쳐 줘 … 둘 다 성공하는 경우가 없어야 함 … 확인 방법: 예약 → 바로 취소 → 3분 넘게 기다려도 PICKED_UP 웹훅이 오지 않는지" | 코드 변경 없이 테스트 10개로 고정 |

후반 프롬프트는 **배경 → 할 일 → 확인 방법 → 보고 형식** 순서로 고정했습니다. 확인 방법을 함께 주니 AI가 구현에서 멈추지 않고 직접 재현까지 했습니다.

### 3. AI에게 거는 규칙

- **승인 게이트** — "커밋과 push는 제가 목록을 확인하고 승인한 뒤에", 커밋 메시지 형식까지 지정
- **실제 상태 보고** — 보고는 설계 / 작성 / 로컬 검증 / 배포 / 운영 검증으로 나누고, 하지 않은 단계는 "미실행"으로 적게 함 (AGENTS.md에 고정)
- **범위 좁히기** — "코드는 안 바꿈", "다른 부분만 고쳐 줘"
- **맥락 넘기기** — "정리본을 프롬프트로 뽑아줘"로 다른 세션에 넘길 요약을 만들게 함

## 회고

AI에게 구현을 맡기면 **사람의 일은 결정과 검증**이 된다는 것을 배웠습니다. 짧게 답해도 grill 질문이 결정할 것을 빠짐없이 끌어냈고, 확인 방법을 명세에 넣자 결과를 믿을 수 있게 됐습니다. 반대로 AI가 합의와 다르게 SQLite 라이브러리를 바꾼 일도 있었는데, 보고는 받았지만 명시적으로 승인하지 않은 채 남아 있습니다. 그래서 "보고"와 "승인"을 구분해 미결 문서에 기록해 두는 습관이 필요하다는 것도 확인했습니다.

Vercel + SQLite 배포 계획의 충돌은 기획 단계에서 AI가 먼저 짚었고, 웹훅 FIFO는 RePlant 수신 규칙이 정해진 뒤 뺐습니다. 둘 다 장애를 겪고 고친 일이 아니라 설계를 바꾼 결정이라 기술 선택 이유에 정리했습니다. FIFO를 뺀 만큼 이벤트 순서는 수신 측 구현에 기대고 있습니다.

**다음 개선 방향**

- 취소와 자동 수거 요청을 실제로 동시에 보내는 부하 테스트
- 운영 데이터가 `courier-data` 볼륨에만 있어, SQLite 백업 주기와 방법 정하기
- `node:sqlite` 변경을 승인할지 확정하기
- 종료(SIGTERM) 중 전송 중인 웹훅을 기다리지 않아, 다음 기동에 같은 `eventId`로 다시 보낼 수 있는 점 정리
- `courierOrderNo`의 6자리 상한(서버 배송 ID가 999999를 넘으면 400) 대응
