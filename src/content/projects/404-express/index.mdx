> **당근 택배를 모방한 모의 택배사** — [RePlant Market](/projects/replant)의 배송 기능이 호출하는 외부 택배사 역할

## 한눈에 보기

- **유형:** 개인 프로젝트 (팀 프로젝트 RePlant의 외부 연동 대상)
- **기간:** 2026.10.08 ~ 2026.10.16
- **작업 방식:** 기획·결정·검증 기준은 직접, 구현은 AI(Claude Code)
- **결과:** 커밋 4개, 테스트 38개 통과, 로컬 Docker에서 RePlant와 양방향 연동 검증
- **배포:** 운영 EC2용 Docker 구성까지 작성 (운영 배포는 하지 않음)

| 구분 | 기술 |
| --- | --- |
| Runtime | Node.js 24, TypeScript |
| API | Express 5, zod |
| Database | SQLite (Node 내장 `node:sqlite`) |
| Test | Vitest, Supertest |
| Deploy | Docker, Docker Compose |

## 문제와 해결 방향

> **문제:** RePlant의 배송 기능을 개발하려면 택배사가 필요한데, 실제 택배사 API는 쓸 수 없다. 그렇다고 단순한 가짜 응답으로는 지연, 실패, 재전송 같은 실제 연동의 어려움을 검증할 수 없다.
>
> **해결:** 실제 택배사처럼 멱등 예약, 시간 기반 상태 진행, 웹훅 재전송을 갖춘 모의 택배사를 만들고, 서버가 꺼져도 이벤트가 유실되지 않게 한다.

## 내 역할과 핵심 기여

- **콘셉트와 규칙 결정** — 당근 택배를 모방한 상태 흐름(예약 → 접수 → 배송 중 → 배송 완료, 수거 전에만 취소)과 부분 취소 규칙
- **계약 설계** — 멱등키 형식 `shipment-yyyyMMdd-NNNNNN`을 서버가 만들어 `Idempotency-Key` 헤더로 보내고, URL에는 송장번호만 쓰는 방식 결정
- **유실 방지 구조 결정** — 웹훅을 기본으로 하되 DB outbox와 재전송, 서버 polling 대사로 보완
- **팀과의 계약 맞추기** — 응답 형식을 팀 Spring 서버의 `ApiResponse {status, code, message, data}`에 맞춰 서버 쪽 클라이언트가 같은 DTO로 파싱하게 함
- **검증 기준 제시** — 기능마다 "확인 방법"을 함께 주고 E2E로 재현하게 함

## 아키텍처

**예약(멱등) → 시간 기반 자동 진행 → 상태 변경을 outbox에 기록 → 웹훅 전송 → 실패 시 재전송 → 5번 실패하면 DEAD**

- 상태 전이와 웹훅 적재를 **한 트랜잭션**으로 묶어, 상태는 바뀌었는데 알림만 빠지는 일이 없게 함
- 같은 멱등키 + 같은 본문은 기존 송장을 200으로, 다른 본문은 409로 응답
- 실패한 웹훅은 DEAD 목록으로 모으고 관리자 API로 수동 재전송

## 주요 구현

1. **멱등 예약** — 응답이 유실돼 서버가 같은 키로 다시 요청해도 송장이 하나만 생김
2. **시간 기반 상태 진행** — 설정한 간격마다 다음 단계로 진행, 간격은 환경변수로 조절
3. **웹훅 outbox와 재전송** — 지수 백오프 재전송 5번, DEAD 목록과 수동 재전송 API
4. **운영 배포 준비** — RePlant와 같은 EC2의 내부 Docker 네트워크에서만 접근하도록 포트를 열지 않는 compose 구성

## AI 활용

이 프로젝트는 **코드 전부를 AI가 작성**했습니다. 대신 무엇을 만들지, 어떤 규칙을 지킬지, 어떻게 확인할지는 직접 정했습니다.

### 1. 질문받으며 기획하기 (grill-me)

`/grill-me` 스킬로 AI가 결정할 것을 라운드별로 질문하고, 매 질문에 추천안을 붙이게 했습니다. 저는 결정만 답했습니다. 6라운드에 걸쳐 멱등키, 알림 방식, 배포 환경, 응답 형식, 재시도 정책을 확정한 뒤 "맞아 시작해줘."로 구현을 시작했습니다. → [기술 기록](/blog/grill-me-planning)

### 2. 프롬프트가 대화에서 명세서로

| 단계 | 프롬프트 (발췌) | 결과 |
| --- | --- | --- |
| 기획 시작 | "가짜 택배사 하나가 필요해 … 당근 택배를 모방해서 … 서버가 꺼져서 이벤트 유실이 되지 않게끔" | grill 질문 라운드 시작 |
| 결정 | "stripe처럼 헤더로 빼고 … courierOrderNo는 url에 붙이지마" | 헤더 멱등키 확정 |
| 문서 골격 | "agent.md는 없어?" | AGENTS.md, CLAUDE.md, 운영·미결 문서 작성 |
| 기능 명세 | "4xx 재전송하지 않음 / 연결 실패, 타임아웃(5초), 5xx: 재전송 / 1분 → 5분 → 30분 → 2시간 → 6시간 … 확인 방법: 서버를 끈 상태에서 배송을 진행 → 재전송 로그 확인" | 재전송 구현과 로컬 재현 |
| 검증 요청 | "다른 부분만 고쳐 줘 … 둘 다 성공하는 경우가 없어야 함 … 확인 방법: 예약 → 바로 취소 → 3분 넘게 기다려도 PICKED_UP 웹훅이 오지 않는지" | 코드 변경 없이 테스트 10개로 고정 |

후반 프롬프트는 **배경 → 할 일 → 확인 방법 → 보고 형식** 순서로 고정했습니다. 확인 방법을 함께 주니 AI가 구현에서 멈추지 않고 직접 재현까지 했습니다.

### 3. AI에게 거는 규칙

- **승인 게이트** — "커밋과 push는 제가 목록을 확인하고 승인한 뒤에", 커밋 메시지 형식까지 지정
- **실제 상태 보고** — 보고는 설계 / 작성 / 로컬 검증 / 배포 / 운영 검증으로 나누고, 하지 않은 단계는 "미실행"으로 적게 함 (AGENTS.md에 고정)
- **범위 좁히기** — "코드는 안 바꿈", "다른 부분만 고쳐 줘"
- **맥락 넘기기** — "정리본을 프롬프트로 뽑아줘"로 다른 세션에 넘길 요약을 만들게 함

### 4. 사람과 AI의 역할 나누기

| 직접 결정 | AI에 맡김 |
| --- | --- |
| 서비스 콘셉트와 상태 흐름, 취소 규칙 | grill 질문 설계와 추천안 |
| 멱등키 형식, 웹훅 + outbox + polling 구조 | 팀 저장소 코드 조사(응답 형식, 서버 PR) |

| 재전송 간격과 4xx 정책 | Docker 구성, 문서, 로컬 E2E 재현 |
| 모든 커밋·push 승인 | 커밋 메시지 초안 |

## 회고

AI에게 구현을 맡기면 **사람의 일은 결정과 검증**이 된다는 것을 배웠습니다. 짧게 답해도 grill 질문이 결정할 것을 빠짐없이 끌어냈고, 확인 방법을 명세에 넣자 결과를 믿을 수 있게 됐습니다. 반대로 AI가 합의와 다르게 SQLite 라이브러리를 바꾼 일도 있었는데, 보고는 받았지만 명시적으로 승인하지 않은 채 남아 있습니다. 그래서 "보고"와 "승인"을 구분해 미결 문서에 기록해 두는 습관이 필요하다는 것도 확인했습니다.
