  problem: "E-Class 과제 크롤링은 결과를 초안 확인 없이 바로 Google Calendar에 등록했다. v1.4.0 작업 중(2026-05-28) '한 번 돌리고 또 돌리면 같은 과제가 중복 등록되지 않나'를 짚었다. 실제로 중복이 쌓인 것을 본 것이 아니라 코드를 따라가 미리 찾은 문제다."
  cause: "등록 함수 CalendarService.addEvent는 항상 events.insert만 호출했고, 크롤러 결과에는 이미 등록된 과제인지 가릴 id가 없었다. 기존 조회 함수(lookupEvent)는 날짜 범위로 찾기 때문에, 마감일이 바뀐 과제는 찾지 못한다는 것도 확인했다. 앞서 DDING!의 학식 크롤러가 실행할 때마다 같은 메뉴를 다시 저장했던 것과 같은 원인이었다."
  solution: "AI가 제안한 중복 키 별도 저장, extendedProperties에 키 넣기, 제목+날짜 비교(오탐) 대신 Google 이벤트 id를 직접 지정하기로 했다. 새 upsertEvent를 만들자는 제안 대신 addEvent 안에서 id가 있으면 events.get으로 조회해 있으면 update, 404면 insert하게 했다. id 재료는 마감일을 빼고 과목(sub)+과제 제목(title)만 공백 정리 후 SHA-256 해시 앞 32자에 calainder 접두사를 붙여, 문서의 id 규칙(base32hex 문자 a~v·0~9, 5~1024자)에 맞췄다(#7)."
  result: "PR 확인 사항에 '크롤링 일정 고정 ID 생성 확인'을 남겼고, 등록 뒤에는 결과를 조회 카드로 다시 보여 준다(#7). 남은 한계: 크롤링을 두 번 돌려 update로 가는지 확인한 기록은 없다. 같은 과목에 같은 제목의 과제가 생기면 id가 겹치고, events.update는 이벤트 전체를 바꾸므로 사용자가 캘린더에서 고친 내용은 다시 크롤링하면 덮어써진다."

  solution: "서버·컨테이너 시간대를 Asia/Seoul로 바꾸는 방법과 코드에서 명시하는 방법 중, 환경이 바뀌어도 흔들리지 않게 get_prompt_context()를 `datetime.now(ZoneInfo(\"Asia/Seoul\"))`로 바꿨다. 종료 시각(명시 없으면 시작 1시간 뒤)·자정 넘김 규칙은 예시와 함께 공통 프롬프트에 모았다. 그래도 틀려 모델을 gpt-4o-mini에서 지시 준수가 낫다고 안내된 gpt-4.1-mini로 바꿨다(gpt-4.1은 비용이 약 5배라 제외, #5). 'N시간 뒤'를 서버가 정규식으로 계산해 덮어쓰는 방법도 검토했지만 모델 교체 뒤 결과가 맞아 넣지 않았다."
  result: "모델을 바꿔 다시 배포한 뒤 배포 서버에서 상대시간 입력을 다시 넣어 결과가 맞는 것을 직접 확인했다. 남은 한계: 확인은 손으로 몇 번 넣어 본 것이 전부라 횟수·실패율 기록이 없고, 자동 회귀 테스트도 없다. 상대시간 계산은 여전히 모델에 맡겨 날짜가 넘어가는 경계에서 다시 틀릴 수 있다."

- title: "AES_KEY 환경변수가 없는 로컬에서 테스트가 ApplicationContext를 띄우지 못하는 문제"
  problem: "v1.5.2에서 REST 경로를 정리하고 `./gradlew test`를 돌리자 CalainderApplicationTests가 ApplicationContext 로드에 실패했다. 그 전에는 로컬에 JAVA_HOME이 잡혀 있지 않아 Gradle 테스트를 아예 돌리지 못하고 있었다."
  cause: "Java는 IntelliJ에 포함된 JetBrains Runtime(Java 21)으로 있었지만 시스템 환경변수에 등록되지 않았다. JAVA_HOME을 잡아 테스트를 실행하자 남은 실패 원인은 AES_KEY였다. CrawlController가 `@Value(\"${aes.key}\")`로 값을 받는데 application.yml의 `aes.key: ${AES_KEY}`에는 기본값이 없고, 같은 원인으로 5월 로컬 실행에서도 `Error creating bean with name 'crawlController'`, `Could not resolve placeholder 'AES_KEY'`가 났었다."
  solution: "실행할 때마다 환경변수를 넣는 방법과 application.yml에 기본값을 두는 방법을 검토했고, 운영 설정에는 기본값을 넣지 않기로 했다. 대신 CalainderApplicationTests의 `@SpringBootTest(properties = ...)`에 테스트 전용 aes.key(16자 테스트 값)와 Google OAuth client-id·secret을 넣어, 운영 비밀값 없이도 컨텍스트가 뜨게 했다. application.yml의 aes.key 들여쓰기도 정리했다(#11)."
  result: "`./gradlew test`와 `git diff --check`를 통과한 뒤 병합했고(#11), 운영 서버에서 calainder-server를 다시 빌드해 서버 안에서 `/` 200과 `/api/auth/status` → `{\"authenticated\":false}`를 확인했다. 브라우저 접속도 정상이었다. 남은 한계: 테스트 파일은 이 컨텍스트 테스트와 ScheduleDTOTest(#4) 두 개뿐이다."

## 문제와 해결 방향

> **문제:** 일정 정보는 메신저, 공지사항, 이미지 캡처처럼 흩어져 있는데, 이를 다시 정리해 캘린더에 입력하는 과정이 번거롭고 반복적이다.
>
> **해결:** 비정형 입력을 AI가 분석하고, 사용자가 이미 쓰는 Google Calendar에 자동으로 반영한다.

## 내 역할과 핵심 기여

- **서버 흐름** — 텍스트·이미지 → AI 분석 → Google Calendar 등록까지를 Controller-Service-DTO/Util 구조로 만들고([#1](https://github.com/gasic37200/Calainder/issues/1)), AI 분석과 Calendar 작업을 별도 API로 나눠 로그인 전에도 분석이 되게 함([#6](https://github.com/gasic37200/Calainder/issues/6))
- **Google 연동** — Google OAuth2 로그인과 Calendar 일정 등록·조회·수정·삭제([#1](https://github.com/gasic37200/Calainder/issues/1)), 반복 일정과 수정 범위 선택([#9](https://github.com/gasic37200/Calainder/issues/9))
- **AI 모듈** — 프롬프트를 공통·텍스트·이미지 규칙으로 나누고 KST 현재 시각을 요청마다 넣음, 모델 교체([#5](https://github.com/gasic37200/Calainder/issues/5)), 한 문장 속 여러 일정을 배열로 분리([#7](https://github.com/gasic37200/Calainder/issues/7))
- **E-Class 크롤링 연동** — 로그인 정보는 AES로 암호화해 크롤러에 전달하고, 고정 이벤트 ID로 재크롤링 시 중복 대신 수정([#7](https://github.com/gasic37200/Calainder/issues/7))
- **배포·운영** — AWS EC2 첫 배포 후 OCI로 옮겨 도메인·Nginx·HTTPS를 구성하고, 모듈별 `.env`·`.dockerignore`로 설정을 나눔([#7](https://github.com/gasic37200/Calainder/issues/7), [#8](https://github.com/gasic37200/Calainder/issues/8))
- **릴리스 관리** — 프로젝트 종료 후 release 브랜치와 PR [#1](https://github.com/gasic37200/Calainder/issues/1) ~ [#11](https://github.com/gasic37200/Calainder/issues/11)로 v1.0.0 ~ v1.5.2를 나눠 병합

Docker 파일(Dockerfile, docker-compose, requirements)은 다른 팀원이 담당했습니다.

## 아키텍처

**사용자 입력 → Spring Boot 서버 → AI 모듈(FastAPI·OpenAI) 또는 E-Class 크롤러 → Google Calendar 반영 → 결과 반환**

- 일정의 최종 저장소를 내부 DB가 아닌 **Google Calendar**로 두어, Repository 계층 없이 Controller-Service-DTO/Util 구조로 단순화
- AI 모듈과 크롤러 모듈은 별도 FastAPI 서비스로 분리해 REST로 호출하고, 운영에서는 내부 네트워크에서만 노출([#7](https://github.com/gasic37200/Calainder/issues/7))
- AI 분석 API는 분석만 맡고, Google Calendar 등록·조회는 별도 API로 분리해 Calendar 작업에만 로그인을 요구([#6](https://github.com/gasic37200/Calainder/issues/6))
- **AI 분석 요청은 동기 흐름**입니다. 화면 버튼 → `fetch` → Spring → FastAPI → OpenAI 응답까지 한 요청 안에서 기다립니다. 비동기는 **E-Class 크롤링만** `CompletableFuture`로 실행하고, 진행 상태를 SSE(`SseEmitter`)로 채팅에 보냅니다([#1](https://github.com/gasic37200/Calainder/issues/1))

## 주요 구현

1. **한 문장 속 여러 일정 분리** — AI 응답을 단일 객체에서 배열로 바꿔 "7시 운동, 9시 도서관" 같은 입력을 일정별 카드로 나눴습니다. 이미지 분석에도 같은 구조를 적용했고, 모델이 객체 하나만 돌려줘도 배열로 감싸 서버가 깨지지 않게 했습니다([#7](https://github.com/gasic37200/Calainder/issues/7)).
2. **로그인 전 분석, 필요할 때만 로그인** — AI 분석은 로그인 없이 되고, Calendar 작업이 401이면 Google 로그인 뒤 하던 작업을 이어서 처리합니다(pending action). 채팅과 일정 초안을 `sessionStorage`에 저장해 로그인 리다이렉트 뒤에도 대화가 사라지지 않게 했습니다([#6](https://github.com/gasic37200/Calainder/issues/6)).
3. **크롤링 중복 방지** — 과목 + 과제 제목으로 만든 고정 이벤트 ID로, 다시 크롤링해도 새로 만들지 않고 기존 일정을 수정합니다([#7](https://github.com/gasic37200/Calainder/issues/7)).
4. **반복 일정** — RRULE로 매일·매주(복수 요일)·매달(복수 날짜) 반복을 만들고, 수정은 "이 일정만"과 "전체 반복 일정"으로 범위를 나눴습니다. 기간 없이 반복 일정을 조회하면 오늘부터 28일을 봅니다([#9](https://github.com/gasic37200/Calainder/issues/9)).
5. **이미지 입력 방어** — JPG·PNG·GIF·WEBP만 받아 HEIC 같은 형식은 요청 전에 안내하고, 이미지 분석이 실패하면 서버 오류 대신 안내 메시지를 돌려줍니다([#2](https://github.com/gasic37200/Calainder/issues/2)).

## 인프라

2026년 4월 AWS EC2에 처음 배포해 `calainder.kr`을 연결했고, 이후 OCI 서버 한 대로 옮겨 Teammate·공용 feedback-api와 함께 Docker Compose로 운영했습니다. 서버 구성, 도메인, Nginx, HTTPS, 배포 반영은 직접 맡았습니다.

| 구성 | 실행 방식 |
| --- | --- |
| Calainder 서버 (Spring Boot) | 컨테이너, Nginx가 80/443에서 받아 프록시 |
| AI 모듈·크롤러 모듈 (FastAPI) | 컨테이너, 내부 네트워크에서만 노출([#7](https://github.com/gasic37200/Calainder/issues/7)) |
| Teammate | 같은 서버의 별도 서비스 (`teammate.o-r.kr`) |
| feedback-api | Calainder·Teammate가 함께 쓰는 FastAPI 모듈, Firestore 저장([#7](https://github.com/gasic37200/Calainder/issues/7)) |
| Nginx | 도메인별 리버스 프록시, HTTPS |

- **서버** — OCI 춘천 리전 A1 Flex(Ubuntu 24.04 ARM), 1 OCPU·4GB로 운영했습니다.
- **설정 분리** — 모듈마다 자기 `.env`를 읽게 하고([#7](https://github.com/gasic37200/Calainder/issues/7)), 모듈별 `.dockerignore`로 `.env`·가상환경·캐시·빌드 결과·크롤러 로그인 상태 파일을 이미지에서 뺐습니다([#8](https://github.com/gasic37200/Calainder/issues/8)).
- **재시작** — 컨테이너에 `restart: unless-stopped`를 걸었습니다([#7](https://github.com/gasic37200/Calainder/issues/7)).
- **배포 반영** — 서버에서 `main`을 받아 바뀐 서비스 이미지만 다시 빌드합니다([#11](https://github.com/gasic37200/Calainder/issues/11)). 선택 의존성을 바꾼 v1.5.1은 캐시 없이 다시 빌드해야 반영됩니다([#10](https://github.com/gasic37200/Calainder/issues/10)).

## 기술 선택 이유

| 결정 | 이유 |
| --- | --- |
| 일정의 최종 저장소를 자체 DB가 아닌 Google Calendar로 | 사용자가 실제로 쓰는 캘린더에 바로 연결되고, 계정·일정 테이블 없이 입력 → 분석 → 반영 흐름에 집중할 수 있음. 일정 히스토리나 분석 로그가 필요해지면 DB를 따로 두는 것으로 확장 |
| Controller-Service-DTO/Util 구조 (Repository 계층 없음) | 저장을 Google Calendar가 맡아 데이터 접근 계층이 필요 없고, 요청 처리·비즈니스 로직·데이터 변환 책임만 나눔 |
| 채팅형 입력 화면 | 자체 캘린더 UI보다 AI에게 요청하는 흐름이 서비스의 핵심 가치에 맞음. 일정 확인·관리는 익숙한 Google Calendar로 넘김 |
| Calendar 권한은 `calendar.events` 범위만 | 일정 등록·수정·삭제가 필요해 읽기 전용으로는 부족하고, 캘린더 설정·공유는 다루지 않아 전체 `calendar` 범위는 필요 없음 |
| E-Class 로그인 정보를 AES 대칭키로 암호화해 크롤러에 전달 | 외부 모듈과 주고받는 과정에서 민감정보가 평문으로 오가지 않게 |
| E-Class 크롤링만 `CompletableFuture`로 실행하고 SSE로 진행 상태 전송 | 로그인·수집 단계별 진행 메시지를 채팅에 실시간으로 보여 주기 위해([#1](https://github.com/gasic37200/Calainder/issues/1)). AI 분석 요청은 동기로 남아 있음 |
| 리마인더를 Google Calendar 알림 옵션과 연결 | 내부에 알림 데이터를 따로 저장하지 않고, 일정 등록과 알림 설정을 한 흐름으로 이음 |

## 회고

팀 프로젝트 당시에는 Git을 협업 도구로 충분히 활용하지 못했습니다. 프로젝트가 끝난 뒤 혼자 보완하면서 release/main 브랜치 분리, PR 반영, cherry-pick과 amend로 버전 이력을 관리하는 방법을 익혔고, 배포 역시 코드·인프라·네트워크·보안 설정이 함께 맞물려야 완성된다는 것을 EC2와 OCI에서 직접 경험했습니다.

AI 분석 요청은 비동기로 처리된다고 생각했지만, 다시 확인해 보니 버튼을 누르면 `fetch`로 Spring·FastAPI·OpenAI를 차례로 기다리는 동기 흐름이었습니다. 비동기는 크롤링(`CompletableFuture` + SSE)뿐이었습니다. 설계 문서에 적은 구조와 실제 코드는 다를 수 있어, 코드로 확인해야 한다는 것을 알게 됐습니다.

Google Calendar 일정 권한(`calendar.events`)은 민감 범위라 Google 검증을 받아야 했습니다. OAuth 동의 화면, 홈페이지 URL, 개인정보처리방침·이용약관 페이지([#4](https://github.com/gasic37200/Calainder/issues/4), [#5](https://github.com/gasic37200/Calainder/issues/5)), 범위 사용 사유, 데모 영상을 준비해 제출했습니다. 검토 중 "홈페이지에 개인정보처리방침 링크가 없다", "로그인 페이지가 홈페이지보다 먼저 표시된다"는 지적을 받아 첫 화면에 약관 링크와 로그인 상태 표시를 넣었지만([#5](https://github.com/gasic37200/Calainder/issues/5), [#11](https://github.com/gasic37200/Calainder/issues/11)), 검증은 반려됐습니다. 외부 플랫폼과 연동할 때는 기능뿐 아니라 "왜 이 권한이 필요한가"까지 증명해야 한다는 것을 겪었습니다.

실제 사용 환경도 달랐습니다. 카카오톡 같은 인앱 브라우저에서는 Google 로그인이 `403: disallowed_useragent`로 막혔고, 모바일에서 입력한 뒤 화면이 깨지는 문제는 `100vh` 고정 높이가 원인이라 `100dvh`로 바꿨습니다([#6](https://github.com/gasic37200/Calainder/issues/6)).

**다음 개선 방향**

- AI 분석 요청을 접수와 결과 조회(polling)로 나누거나 큐에 넣어, OpenAI 응답을 기다리는 동안 요청이 붙잡혀 있지 않게 하기
- "N시간 뒤·N분 뒤" 같은 상대시간은 서버가 직접 계산해 모델 결과를 보정하기
- 테스트 늘리기: 크롤링을 다시 돌렸을 때 수정되는지, 상대시간 입력별 결과 (지금은 테스트 파일 2개)
- 일정 히스토리와 분석 로그가 필요해지면 별도 저장소 두기
