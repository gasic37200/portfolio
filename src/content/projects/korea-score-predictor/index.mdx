## 문제와 해결 방향

> **문제:** 매장 고객은 빠르게 이벤트에 참여해야 하고, 운영자는 상대팀과 마감 시간을 자주 바꿀 수 있어야 하며, 휴대폰 번호는 안전하게 처리되어야 한다.
>
> **해결:** QR 진입용 모바일 폼, 관리자 경기 관리 화면, 서버 사이드 개인정보 처리, 경기별 중복 참여 제약을 하나의 MVP로 구성한다.

## 내 역할과 핵심 기여

- 경기별 중복 참여를 `match_id + phone_hash` 기준으로 제한하고 DB 유니크 제약으로 보장
- 휴대폰 번호 해시·마스킹·선택적 암호화 정책을 설계해 원본 노출 지점을 CSV export 한 곳으로 축소
- 관리자가 경기 추가, 수정, 표시/숨김, 실제 결과 입력을 직접 할 수 있는 운영 화면 구현
- Codex + 작업 하네스로 요구사항 → 구현 → SQL migration → 검증 → 배포 확인을 반복 가능한 흐름으로 관리

## 아키텍처

**QR 접속 → 이벤트 폼 → Server Action 검증 → Supabase 저장 → 결과 집계 → 관리자 운영**

| 경로 | 역할 |
| --- | --- |
| `/event` | 사용자 입력과 경기 스코어 예측 제출 |
| `/result` | 경기별 참여자 수와 스코어 분포 |
| `/admin/matches` | 경기 추가, 수정, 표시/숨김, 실제 결과 입력 |
| `/admin/export` | 실제 결과와 일치한 당첨자 CSV export |

민감한 로직은 Server Action과 server-only helper에서만 처리하고, service role key·해시 secret·암호화 key는 브라우저로 전달되지 않도록 했습니다. 데이터는 `events`, `matches`, `participants`, `predictions`, `score_distribution` view로 나누었습니다.

## 주요 구현

1. **서버 기준 제출 검증** — 클라이언트가 보낸 경기 정보를 믿지 않고, 서버가 열린 경기와 마감 시간을 다시 조회해 제출 가능 여부를 판단
2. **부분 저장 방지** — 예측 저장에 실패하면 직전에 만든 참여자 row를 삭제
3. **한 번에 한 경기만 노출** — 새 경기를 표시하면 같은 이벤트의 나머지 경기는 자동 숨김
4. **모바일 UX** — 휴대폰 번호 자동 포맷, 제출 실패 시 입력값 유지, 마감 카운트다운, 마감 후 제출 버튼 비활성화

## 기술 선택 이유

| 결정 | 이유 |
| --- | --- |
| 민감한 로직은 Server Action과 server-only helper에서만 처리 | Supabase service role key, 해시 secret, 암호화 key가 브라우저로 넘어가지 않게 |
| 제출 시 경기·마감 시간을 서버에서 다시 조회 | 클라이언트가 보낸 경기 정보를 그대로 믿지 않고 열린 경기와 마감 기준으로 판단 |
| 중복 참여를 애플리케이션 조회 + DB 유니크 제약(`participants_match_phone_unique`)으로 이중 차단 | 애플리케이션 조회를 통과한 요청도 DB 제약이 한 번 더 막음 |
| 번호 비교는 해시, 표시는 마스킹, 연락은 암호화로 분리 | 중복 비교·화면 표시·당첨자 연락이라는 서로 다른 요구를 원본 번호 하나로 처리하지 않기 위해 |
| 경기 정보를 seed가 아닌 관리자 화면에서 수정 | 토너먼트 상대팀이 당일에 바뀌는 이벤트라 개발자가 매번 seed를 고치는 구조가 맞지 않음 |
| 요구사항·정책을 `SPEC.md`·`PRIVACY.md` 등 문서로 고정하고 lint·typecheck·build로 변경마다 검증 | 기능을 빠르게 바꾸면서도 개인정보 정책, DB 제약, 관리자 UX, 배포 체크리스트가 서로 어긋나지 않게 |
