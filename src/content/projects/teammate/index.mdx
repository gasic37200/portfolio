- title: "Spring이 보낸 JSON을 FastAPI가 빈 본문으로 받아 422를 돌려주는 문제"
  problem: "보완 개발 중 로컬 Windows에서 평가 웹 서버(Spring Boot)가 AI 평가 모듈(FastAPI)에 개발자 평가를 요청하면 422 Unprocessable Entity가 났다. FastApiExceptionMapper 로그는 {\"type\":\"missing\",\"loc\":[\"body\",\"github_name\"],\"msg\":\"Field required\"}였고, Uvicorn은 같은 요청에서 Unsupported upgrade request., Invalid HTTP request received. 경고를 냈다. 개발자 평가가 요청 검증 단계에서 거절돼 평가 함수까지 가지 못했다."
  cause: "FastAPI 검증 전에 넣은 임시 로그는 content-type: application/json, raw body: b''였고, 같은 요청의 Spring 전송 로그는 bodyLength=28, body={\"github_name\":\"...\"}였다. Postman으로 FastAPI를 직접 부르면 정상이어서, Spring이 만든 본문이 Uvicorn이 읽는 단계에서 비는 것으로 범위를 좁혔다. 같은 구조로 동작하던 Calainder와 가상환경을 비교하니 두 requirements.txt 모두 버전 없는 uvicorn[standard]였지만 설치 시점이 달라 uvicorn 0.38.0 / 0.48.0이었고, httptools 0.8.0은 Teammate에만 있었다. Calainder 버전으로 다시 설치해도 422가 그대로여서 버전이 아니라 httptools 유무를 차이로 봤다. Uvicorn 기본값 --http auto는 httptools가 설치돼 있으면 그것을 HTTP 파서로 쓰므로, Teammate는 httptools, Calainder는 h11로 요청을 읽고 있었다."
  solution: "처음에는 422를 요청 형식 문제로 보고 Content-Type 명시와 Gradle 재빌드를 했지만 같았다. Spring HTTP 클라이언트를 SimpleClientHttpRequestFactory로 바꾼 실험은 원인이 섞인다고 보고 되돌린 뒤, Spring 코드는 그대로 두고 AI 모듈만 --http h11로 띄워 파서 하나만 바꿔 비교했다. v1.0.0은 Dockerfile CMD에 --http h11을 넣어 배포했고(#1), 이후 WebSocket을 쓰지 않으므로 requirements.txt의 uvicorn[standard]를 uvicorn으로 바꿔 httptools를 아예 설치하지 않고 --http h11은 뺐다. 이 변경은 Calainder release/v1.5.1(PR 10)로 먼저 병합했고, Teammate는 로컬 커밋 45b72f9로만 만들어 두었다."
  result: "Spring 코드를 바꾸지 않고 AI 모듈만 --http h11로 띄우자 같은 개발자 평가 요청이 422 없이 처리됐다. 다음 날 운영 서버의 Calainder에서도 AI 컨테이너 안 직접 호출은 200인데 Spring을 거치면 본문이 비는 같은 증상이 나와, 같은 의존성 정리를 PR 10으로 적용했다. 남은 한계: Teammate 원격 저장소에는 아직 uvicorn[standard]와 --http h11이 남아 있고 버전도 고정하지 않았다. httptools에서 본문이 비는 정확한 동작과, 정리 후 Calainder의 Spring 경유 요청 결과는 확인해 기록하지 않았다."

## 문제와 해결 방향

> **문제:** 팀 프로젝트를 하고 싶어도 지원자의 실질적인 역량과 협업 성향을 객관적으로 파악하기 어렵다.
>
> **해결:** 역할·기술·성향을 프로필로 구조화하고, 직군별 AI 역량 등급으로 지원자의 실력을 비교하게 한다. 성격 유형 기반 매칭은 기획 단계까지 진행했다.

## 내 역할과 핵심 기여

- **팀장·기획 총괄** — 구인 게시판은 기존 플랫폼과 차별성이 약하다는 중간 피드백을 받고, **프로필 기반 헤드헌팅 구조**로 방향을 바꿈
- **AI 역량 평가 모듈** — 개발자·디자이너·기획자 3개 직군을 항목 7개씩 가중치로 점수화하고, Trainee부터 Master까지 13단계 등급으로 환산하는 FastAPI 모듈([#1](https://github.com/gasic37200/teammate/issues/1))
- **서버 연동** — Spring Boot 평가 웹 서버가 FastAPI 평가 모듈을 REST로 호출하고, 직군별 입력 검증을 서버에서 먼저 해 잘못된 요청이 AI 호출까지 가지 않게 함([#1](https://github.com/gasic37200/teammate/issues/1))
- **보완 개발과 배포** — 프로젝트 종료 후 평가 기능을 독립 실행 가능한 웹 서버로 만들어 `teammate.o-r.kr`에 배포([#1](https://github.com/gasic37200/teammate/issues/1), [#2](https://github.com/gasic37200/teammate/issues/2))
- **발표·문서화** — 중간 발표, 결과 보고서, 소개 영상과 모션그래픽 제작

팀 앱(Flutter, `teammate-app`)의 화면 구현과 디자인은 다른 팀원이 담당했습니다.

## 아키텍처

**(보완 개발한 평가 서비스) 평가 화면 → Spring Boot 웹 서버 → FastAPI AI 평가 모듈(OpenAI API) → 등급 결과 반환**

- 웹 서버(`teammate-web`)와 AI 모듈(`teammate-ai-grading`)을 Docker Compose 서비스로 나누고, AI 모듈은 외부 포트를 열지 않아 웹 서버만 컨테이너 네트워크 안에서 호출
- 피드백은 Calainder와 함께 쓰는 공용 `feedback-api`(FastAPI + Firestore)를 `FEEDBACK_API_BASE_URL`로 호출해, 서비스마다 피드백 기능을 따로 만들지 않음
- Nginx 리버스 프록시와 HTTPS로 `teammate.o-r.kr`에 연결

## 주요 구현

1. **OpenAI API 하나로 통합** — 학교 제공 FactChat API에 묶여 있던 호출을 걷어내고, 3개 직군 평가를 모두 같은 OpenAI 클라이언트로 호출해 평가 흐름을 하나의 API 위에서 관리
2. **입력 검증** — GitHub 이름이 비었거나, 디자이너 이미지·기획서 PDF가 없거나, 지원하지 않는 직군이면 AI를 호출하기 전에 거절
3. **예외 구분** — `FastApiExceptionMapper`가 FastAPI 응답이 4xx면 입력 오류(경고 로그), 5xx면 모듈 장애(에러 로그)로 나누고, 응답 본문의 `message`나 `detail`을 사용자에게 보여 줄 메시지로 꺼냄. `feedback-api` 호출에도 같은 기준 적용
4. **로그인 없는 피드백 관리** — 브라우저에서 만든 UUID를 `localStorage`에 저장해, 로그인 기능이 없는 평가 화면에서도 같은 브라우저의 피드백을 이어서 조회·수정

## 인프라

| 구분 | 구성 |
| --- | --- |
| 서버 | OCI A1 Flex(Ubuntu 24.04 ARM) 1대. Calainder, 공용 `feedback-api`와 함께 운영 |
| 컨테이너 | Docker Compose 서비스 `teammate-web`, `teammate-ai-grading`, `restart: unless-stopped` |
| 진입점 | Nginx 리버스 프록시 + HTTPS (`teammate.o-r.kr`) |
| 네트워크 | DNS, Internet Gateway, Route Table, Security List, Linux 방화벽 직접 설정 |

- AI 모듈의 API 키는 `env_file`로 실행할 때 주입하고, 모듈별 `.dockerignore`로 `.env`·가상환경·빌드 결과가 이미지에 들어가지 않게 함([#1](https://github.com/gasic37200/teammate/issues/1))
- 웹 프로젝트의 중첩 디렉터리를 정리하고 Compose 빌드 경로를 맞춤([#2](https://github.com/gasic37200/teammate/issues/2))
- v1.0.0을 올릴 때는 Docker Desktop이 꺼져 있어 로컬 이미지 빌드는 확인하지 못함([#1](https://github.com/gasic37200/teammate/issues/1) 본문)

프로젝트 중간에 디자이너가 이탈했고, 팀 전체가 Git 협업에 익숙하지 않았으며, 마감 시간도 부족했습니다. 그래서 최종 앱은 더미데이터 중심으로 동작했습니다. 팀장으로서 모든 기능을 완성하기보다 **서비스의 존재 이유를 설명할 수 있는 기획과 핵심 흐름**을 남기는 데 집중했고, 제가 담당한 AI 평가 모듈은 별도로 완성도 있게 구현했습니다. 이 경험으로 프로젝트 전체 완성도와 개인 담당 기능의 완성도를 분리해서 관리하는 법을 배웠습니다.

학기가 끝났을 때 AI 평가 모듈은 앱과 분리돼 있어 직접 실행해 볼 수 없었습니다. 그래서 종료 후 평가 기능만 Spring Boot 웹 서버로 감싸 Docker Compose로 OCI에 올리고 Nginx와 HTTPS를 붙였습니다. 이 과정에서 Dockerfile, compose, 환경변수, 보안 규칙, Nginx, DNS 중 하나만 어긋나도 서비스가 뜨지 않는다는 것을 겪었습니다. 422 문제에서는 처음에 요청 형식부터 고치느라 시간을 썼고, 원본 본문을 찍어 보고 정상 동작하던 Calainder와 설치 패키지를 비교한 뒤에야 원인이 좁혀졌습니다.

**다음 개선 방향**

- 로컬에만 있는 의존성 정리 커밋(`uvicorn[standard]` → `uvicorn`, `--http h11` 제거)을 원격에 올리고, `requirements.txt`의 버전을 고정해 설치 시점에 따라 동작이 달라지지 않게 한다
- 자동 테스트가 Spring 컨텍스트 로드 1개뿐이라, 웹 서버 → AI 모듈 요청이 본문까지 전달되는지 확인하는 연동 테스트를 추가한다
