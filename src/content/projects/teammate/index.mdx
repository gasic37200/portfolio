## 문제와 해결 방향

> **문제:** 팀 프로젝트를 하고 싶어도 지원자의 실질적인 역량과 협업 성향을 객관적으로 파악하기 어렵다.
>
> **해결:** 역할·기술·성향을 프로필로 구조화하고, AI 역량 등급과 성격 유형 분석으로 팀에 맞는 인재를 탐색하게 한다.

## 내 역할과 핵심 기여

- **팀장·기획 총괄** — 중간 피드백에서 차별성이 약하다는 지적을 받고, 구인 게시판을 **프로필 기반 헤드헌팅 구조**로 재정의
- **AI 역량 평가 모듈** — 직군별 평가 기준과 가중치를 설계하고 FastAPI 모듈로 구현
- **서버 연동** — FastAPI AI 모듈과 Spring Boot 서버 간 통신 구조 구현
- **보완 개발과 배포** — 프로젝트 종료 후 평가 기능을 독립 실행 가능한 웹 서버로 만들고 OCI에 배포
- **발표·문서화** — 중간 발표, 결과 보고서, 홍보 영상과 모션그래픽 제작

## 아키텍처

**평가 화면 → Spring Boot 웹 서버 → FastAPI AI 평가 모듈(OpenAI API) → 등급 결과 반환**

- `teammate-web`과 `teammate-ai-grading`을 Docker Compose 서비스로 분리
- Calainder와 함께 쓰는 공용 `feedback-api`(FastAPI + Firestore)를 별도 모듈로 분리
- Nginx 리버스 프록시와 HTTPS로 `teammate.o-r.kr`에 연결

## 주요 구현

1. **직군별 AI 평가 고도화** — 학교 제공 FactChat API 의존 구조를 정리하고 OpenAI API 중심으로 통합
2. **예외 처리** — AI 모듈의 `detail` 응답을 해석하는 `FastApiExceptionMapper`로 사용자 입력 오류와 외부 모듈 오류를 구분
3. **입력 검증** — 직군별 입력값 검증을 서버에서 먼저 수행해 잘못된 요청을 차단
4. **로그인 없는 피드백 관리** — 브라우저에서 만든 식별자로 같은 사용자의 피드백을 조회·수정

## 기술 선택 이유

| 결정 | 이유 |
| --- | --- |
| Spring Boot 평가 웹 서버를 추가하고 FastAPI AI 모듈과 REST로 연동 | 학기 종료 시점의 AI 모듈은 앱과 분리돼 직접 실행해 볼 수 없었음. 팀 앱 전체를 다시 만들기보다 담당한 평가 기능을 독립적으로 체험할 수 있게 하는 데 집중 |
| 학교 제공 FactChat API를 걷어내고 OpenAI API로 통합 | 프로젝트 당시 학교가 제공하던 API에 묶인 구조를 정리해, 직군별 평가 흐름을 하나의 API 위에서 관리 |
| `FastApiExceptionMapper`로 AI 모듈의 `detail` 응답 해석 | 사용자 입력 오류와 외부 모듈 오류를 구분해 화면에 다르게 알리기 위해 |
| 공용 `feedback-api`(FastAPI + Firestore)를 별도 모듈로 분리 | Calainder와 Teammate가 함께 쓰는 피드백 기능이라 서비스마다 따로 만들지 않음 |
| 브라우저에서 만든 식별자로 피드백 조회·수정 | 평가 화면에 로그인 기능이 없어도 같은 사용자의 피드백을 이어서 관리하기 위해 |
| `teammate-web`, `teammate-ai-grading`을 Docker Compose 서비스로 분리, 모듈별 `.dockerignore` | 한 OCI 서버에서 Calainder·Teammate·feedback-api를 서비스별 컨테이너로 운영하고, 이미지에 `.env`·가상환경·캐시가 들어가지 않게 |

## 회고

프로젝트 중간에 디자이너가 이탈했고, 팀 전체가 Git 협업에 익숙하지 않았으며, 마감 시간도 부족했습니다. 그래서 최종 앱은 더미데이터 중심으로 동작했습니다. 조장으로서 모든 기능을 완성하기보다 **서비스의 존재 이유를 설명할 수 있는 기획과 핵심 흐름**을 남기는 데 집중했고, 제가 담당한 AI 평가 모듈은 별도로 완성도 있게 구현했습니다. 이 경험으로 프로젝트 전체 완성도와 개인 담당 기능의 완성도를 분리해서 관리하는 법을 배웠습니다.
