# 프로젝트 페이지 양식

`src/content/projects/<slug>/index.mdx`를 새로 쓰거나 고칠 때 이 양식을 따른다. 기준 페이지는 RePlant(`/projects/replant`)다. 자료가 없는 섹션은 비워 두지 말고 통째로 뺀다(빈 제목을 남기지 않는다).

## 1. 페이지 구조

| 순서 | 섹션 | 필수 | 들어가는 것 |
| --- | --- | --- | --- |
| 0 | frontmatter | 필수 | `title`, `summary`, `date`, `tags`, `demoUrl`, `repoUrl`, `troubleshooting` |
| 1 | `## 한눈에 보기` | 필수 | 유형·기간·인원·역할·배포 bullet + 기술 표 |
| 2 | `## 시연 영상` 또는 `## 소개 영상` | 영상 있을 때 | `<YouTube id title />` + 한 줄 설명 |
| 3 | `<Planning>` 기획 토글 | 기획 자료 있을 때 | `<PlanItem>` 항목들 |
| 4 | `## 문제와 해결 방향` | 필수 | 인용 블록 두 줄 |
| 5 | `## 내 역할과 핵심 기여` | 필수 | bullet 3~6개 |
| 6 | `## 아키텍처` | 필수 | 굵은 흐름 한 줄 + 설명 (+ 그림, ERD 토글) |
| 7 | `## 주요 구현` | 필수 | 번호 목록 3~5개 (+ API 명세·결정 기록 토글) |
| 8 | `## 테스트와 검증` | 자료 있을 때 | PR별 표 |
| 9 | `## 인프라` | 직접 운영했을 때 | 구성 표 + bullet + 운영 문제 토글 |
| 10 | `## 기술 선택 이유` | 자료 있을 때 | 결정 표 |
| 11 | `## AI 활용` | AI로 작업했을 때 | SKILL.md "AI 활용 섹션" |
| 12 | `## 트러블슈팅` | 필수 | `<Troubleshooting items={frontmatter.troubleshooting} repo={frontmatter.repoUrl} />` |
| 13 | `## 회고` | 필수 | 문단 + `**다음 개선 방향**` bullet |

페이지 위쪽(1~3)은 "무슨 서비스인지", 아래쪽(4~13)은 "내가 무엇을 했고 어떻게 증명하는지"다.

### 섹션별 양식

**frontmatter `summary`** — 한두 문장. 무엇을 만들었는지 + 내 역할 또는 결과.

```yaml
summary: "직접 키운 식물을 사고파는 C2C 마켓. 5인 팀의 팀장으로 배송·알림 모듈과 팀 인프라를 맡아 replant.kro.kr로 운영했습니다."
```

**한눈에 보기**

```mdx
## 한눈에 보기

- **유형:** 팀 프로젝트 (세미 프로젝트)
- **기간:** 2026.10.06 ~ 2026.10.22
- **인원:** 5인
- **역할:** **팀장**, 배송·알림 모듈, …
- **배포:** AWS EC2 + Docker Compose + Nginx(HTTPS)로 운영

| 구분 | 기술 |
| --- | --- |
| Front | … |
| Backend | … |
| Data | … |
| Infra | … |
```

- 기술 표는 **Front를 맨 위**에 두고 Backend → Data/실시간 → Infra 순서.
- 기여 수치(PR 수 등)가 확인되면 `**기여:**` 줄을 넣는다.

**영상** — 기능을 보여 주면 `## 시연 영상`, 서비스 콘셉트면 `## 소개 영상`. 아래에 "무엇을 어떤 순서로 보여 주는지" 한 줄.

**기획 토글**

```mdx
<Planning summary="항목1 · 항목2 · 항목3">

<PlanItem title="항목 제목" links={[{ label: "Figma 보드", href: "https://…" }]}>

설명 한두 문장. 형식은 "기준(목록)과 기준(목록)으로 ~했습니다".

![대체 텍스트](/images/projects/<slug>/<file>.webp)

</PlanItem>

</Planning>
```

- 기획은 기술 기록 글로 따로 빼지 않고 이 토글 한곳에 모은다.
- 항목 순서: 전체 흐름 → 유스케이스 → 이벤트 스토밍 → 바운디드 컨텍스트 → ERD → 와이어프레임 → 컨벤션 → 서비스 정책 → 저장소. 없는 항목은 뺀다.
- 원본 자료 링크는 그 항목의 `links`에 단다. 로그인해야 열리는 자료(비공개 노션, claude.ai 캔버스)는 걸지 않는다.
- 사람 얼굴 사진이 든 자료는 흐리게 처리한다.

**문제와 해결 방향**

```mdx
> **문제:** 사용자·운영 관점의 문제 한 문장.
>
> **해결:** 그래서 무엇을 만들었는지 한 문장.
```

**내 역할과 핵심 기여** — `**영역** — 한 일([#PR](링크), …)` 형식. 팀 프로젝트면 마지막 줄에 "○○는 다른 팀원이 담당했습니다."로 경계를 긋는다. 팀원 이름은 쓰지 않는다.

**아키텍처** — `**A → B → C**` 흐름 한 줄로 시작하고, 설계 원칙 bullet 3~5개.

**주요 구현** — `1. **제목** — 무엇을 어떻게` 3~5개. "~를 구현했다"로 끝내지 말고 **무엇을 막거나 줄였는지**를 쓴다.

**테스트와 검증**

```mdx
| PR | 추가한 테스트 | 확인한 것 |
| --- | --- | --- |
| 기능 이름 [#123](…/issues/123) | Testcontainers 3개 | 커밋 전 미호출·커밋 후 저장, 롤백 시 미호출 |
```

숫자(테스트 개수, 전체 통과 수, 측정값)는 PR 본문에 적힌 값만 쓴다.

**기술 선택 이유**

```mdx
| 고른 것 | 다른 선택지 | 이유 |
| --- | --- | --- |
| … | … | 이유. 대신 감수한 점 |
```

다른 선택지가 자료에 없으면 `| 결정 | 이유 |` 두 칸 표로 쓴다. 대안을 지어내지 않는다.

**회고** — 문단 1~2개(배운 점, 자체 평가) + `**다음 개선 방향**` bullet. 트러블슈팅 박스의 "남은 한계"는 여기서 다시 모아 적는다.

### 공통 규칙

- 한눈에 보기 앞에 한 줄 인용(`> **한 줄 소개** — 팀명·과정`)은 둬도 된다. 없어도 된다.
- AI 자료가 "AI에게 거는 규칙" 정도뿐이면 `## AI 활용` 섹션 대신 회고 아래 `<details>` 토글로 둔다(Korea Score Predictor 방식).
- 근거 위치: PR로 협업했으면 PR 번호, 개인 저장소면 PR(있을 때)·커밋 해시·릴리스 브랜치. 사용자가 PR 본문과 다르게 기억하면 사용자 말을 따르고 SKILL.md 미결 사항에 남긴다.

- 문장은 `~했다`(박스·표) 또는 `~했습니다`(본문 문단). 짧게 끊는다.
- `#123`은 모두 `[#123](https://github.com/<repo>/issues/123)` 링크로. PR 번호는 PR로 협업한 팀 프로젝트에만 있다. 개인 프로젝트처럼 PR이 없으면 릴리스 브랜치·커밋으로 근거를 대거나 생략하고, 번호를 지어내지 않는다.
- 이미지는 `public/images/projects/<slug>/`에 WebP로.
- 표는 전역 스타일로 테두리가 그려진다. 첫 열은 짧은 이름, 마지막 열에 긴 설명.

공통점은 네 가지다. **증상을 원문대로**, **원인을 어떻게 찾았는지**, **왜 그 해결을 골랐는지**, **결과를 숫자나 테스트로**.

### 박스 양식 (STAR)

2026-10-28 사용자 기준: 박스는 `현상 → 원인 분석 및 근거 → 해결 방안 → 결과 및 검증` 네 칸이다(화면 라벨도 이 이름). frontmatter 키는 그대로 `problem / cause / solution / result`.

```yaml
- title: "{어떤 상황}에서 {무슨 증상}이 생기는 문제"
  problem: "[현상] 어디서·어떤 요청에서. 에러 로그·메시지·HTTP 상태 코드를 `코드` 원문 그대로. [영향] 무엇이 깨졌는지, 숫자가 있으면 숫자."
  cause: "[근거] 무엇을 보고 판단했는지: 로그 내용, 스택 트레이스, 설정 파일 값, 버전 비교, 재현 조건. [원인] 그 근거로 확정한 원인을 수치·설정 값으로. 처음 판단이 틀렸다면 그것도."
  solution: "[시도] 시도한 방법과 안 된 이유. [최종 해결] 무엇을 어떤 값·코드로 바꿨는지(파일, 설정 키, 값). 근거가 있으면 끝에 (#PR) 또는 커밋."
  result: "[검증] 해결을 증명하는 데이터: 성공 로그, 응답 코드, 테스트 이름·개수, 반복 횟수와 실패율, 전후 수치. [남은 한계] 확인하지 못한 것."
  post: "blog-slug"   # 관련 기술 기록이 있을 때만
```

나쁜 예와 좋은 예 (사용자가 준 기준):

- ❌ "에러가 자꾸 났다 / 등록이 잘 안 됐거나 타임아웃인 것 같았다 / 설정을 이것저것 바꾸니 됐다" — 추측, 근거 없음.
- ⭕ "`POST`에서 간헐적 `504 Gateway Timeout` / Gateway 로그의 `TimeoutException`, 외부 API 평균 2.5초, 라우팅 타임아웃 `1000ms` / `response-timeout`을 `3000ms`로 / 100회 연속 테스트에서 504 0%".

칸마다 대괄호 요소를 모두 채울 필요는 없다. **자료에 있는 것만** 쓴다. 로그·설정 값·수치를 지어내지 않는다. 아래 두 가지가 없으면 박스로 만들지 않고 회고 문단에 넣는다.

- 원인의 근거 (로그, 설정, 비교, 재현 중 하나)
- 결과의 근거 (수치, 테스트, 성공 로그, 운영 확인 중 하나)

### 칸별 체크리스트

| 칸 | 꼭 | 하지 말 것 |
| --- | --- | --- |
| title | 증상이 보이는 제목 ("~하는 문제") | 해결책을 제목에 쓰기 ("@Version 적용") |
| problem | 에러 로그·메시지·상태 코드 원문 | 원인을 미리 쓰기, "에러가 났다"로 끝내기 |
| cause | 판단 근거(로그, 트레이스, 설정 값, 비교)와 그로 확정한 원인 | "~인 것 같았다", 근거 없는 한 줄 |
| solution | 시도한 것과 최종 변경(파일·설정 키·값), 근거 위치 | "이것저것 바꿨다", 팀이 한 일을 내가 한 것처럼 쓰기 |
| result | 성공 로그·응답 코드·테스트·반복 횟수·전후 수치, 남은 한계 | "안정성이 향상됐다"처럼 측정 없는 말 |

### 예시 (RePlant 박스 1)

```yaml
- title: "결제가 롤백돼도 택배 예약만 남는 문제"
  problem: "처음 구현(#103)은 결제 트랜잭션 안에서 택배사 예약 API를 호출했다. 결제가 뒤 단계에서 롤백되면 택배사에는 예약만 남고, 택배사 응답(최대 5초)을 기다리는 동안 결제 트랜잭션도 열려 있었다."
  cause: "외부 API 호출은 DB 트랜잭션의 롤백 대상이 아닌데, 호출이 트랜잭션 경계 안에 있었다."
  solution: "배송 생성을 두 단계로 나눴다. … 첫 시도에서는 콜백 안의 저장이 커밋되지 않았는데, Testcontainers PostgreSQL 통합 테스트로 이를 발견하고 PROPAGATION_NOT_SUPPORTED로 트랜잭션을 떼어 냈다. …(#149)."
  result: "통합 테스트로 '커밋 전 미호출·커밋 후 BOOKED' …를 고정했다(전체 392개 통과). 남은 한계: 택배사가 느리면 결제 응답이 배송 1건당 최대 8초(타임아웃 합계) 늦어질 수 있어, 카오스 테스트와 비동기 전환·서킷 브레이커를 다음 과제로 정했다."
```

- problem: 상황(처음 구현) + 증상(예약만 남음) + 영향(최대 5초 트랜잭션 점유)
- solution: 첫 시도가 실패한 것과 그걸 무엇으로 찾았는지까지
- result: 테스트로 고정한 것 + 남은 한계(측정하지 않은 값은 "~수 있다"로)

### 박스 고르는 기준

- 한 프로젝트에 3~6개. 면접에서 10분 이상 이야기할 수 있는 것부터.
- 내가 직접 원인을 찾고 해결한 것만. 팀원이 해결한 문제는 쓰지 않는다.
- 해결하지 못한 문제도 원인과 배운 점이 분명하면 박스가 된다(solution에 실제로 한 대응, result에 배운 점과 이후 개선).
- 깊게 쓸 만한 것은 기술 기록 글(`/blog`)로 따로 쓰고 `post`로 잇는다.

## 3. 기술 기록 양식 (결정 기록)

트러블슈팅 박스와 기술 기록은 역할이 다르다. 같은 내용을 두 번 쓰지 않는다.

| | 트러블슈팅 박스 (프로젝트 페이지) | 기술 기록 (`/blog`) |
| --- | --- | --- |
| 답하는 질문 | 무슨 일이 있었고 어떻게 고쳤나 | **왜 그 방법을 골랐나** |
| 중심 | 증상 → 원인 → 해결 → 결과 | 제약 → 선택지 비교 → 결정 근거 → 감수한 것 |
| 길이 | 칸마다 한두 문장 | 5분 분량 |

2026-10-27 멘토 피드백: "기술 기록이 트러블슈팅과 같다. 원인 칸의 결과가 원인의 근거처럼 읽힌다. 왜 이 방식을 택했는지가 구체적으로 나와야 한다." 그래서 기술 기록은 결정 기록(ADR) 형태로 쓴다.

2026-10-28 사용자 기준: 모든 기술 기록은 `sse-jwt-async-dispatch` 글을 본보기로 한다.

- **제목은 내가 해 본 기술을 `~하기`로.** 증상이나 오류 이름을 제목에 쓰지 않는다. 예: "JWT로 인증하는 서버에 SSE 실시간 알림 붙이기" (O), "422 오류 원인 좁히기" (X).
- **트러블슈팅과 분리.** 기술 기록에는 `troubleshooting` frontmatter를 두지 않고 `decision`만 둔다. 오류 경위는 프로젝트 페이지 박스 몫이고, 글에서는 `구현하며 부딪힌 것`에 한두 문단으로만 쓴다.
- **원리를 먼저 설명한다.** 그 기술이 어떻게 동작하는지(`## 먼저 알아야 할 원리`)를 배경 다음에 둔다. 원리는 공식 문서·소스 코드로 확인한 것만.

### frontmatter

```yaml
decision:
  question: "결정해야 했던 질문 한 문장 (예: 결제가 끝난 주문의 택배 예약을 언제, 어떻게 호출할까)"
  choice: "고른 방법 한 문장"
  reasons:
    - "기준 1에 비춘 이유"
    - "기준 2에 비춘 이유"
  tradeoff: "이 선택으로 감수한 것과 언제 다시 볼지"
```

`decision`이 있으면 글 상단에 "결정해야 했던 것 / 고른 방법 / 고른 이유 / 감수한 것" 상자가 그려지고, `troubleshooting` 상자는 그리지 않는다.

### 본문 순서

1. `## 배경과 제약` — 무엇을 만들고 있었고, 지켜야 할 조건이 무엇이었는지. 외부 API의 성질(느림, 실패, 멱등 지원), 팀 규칙, 기간, 인프라 제약. **결정 기준은 여기서 나온다.**
1-1. `## 먼저 알아야 할 원리` — 결정에 영향을 준 동작 원리를 `###` 소제목 여러 개로. 그림이나 짧은 코드가 있으면 좋다.
2. `## 결정해야 했던 것` — 증상이 아니라 질문으로. 처음 구현에서 드러난 문제는 여기서 한두 문장으로만(자세한 경위는 트러블슈팅 박스 몫).
3. `## 검토한 선택지` — 표 `| 선택지 | 장점 | 단점 | 이 프로젝트에서 |`. 실제로 검토·시도한 것만 넣는다. 검토하지 않은 대안을 지어내지 않는다. 검토하지 않았지만 지금 보면 비교할 만한 것은 "돌아보면" 표시로 따로 구분한다.
4. `## 결정과 근거` — 1번의 기준 하나하나에 고른 방법이 어떻게 답하는지. "A라서 B를 골랐다"가 기준마다 한 문장씩.
5. `## 구현하며 부딪힌 것` — 결정을 코드로 옮기며 생긴 시행착오(예: 콜백 안의 저장이 커밋되지 않음)와 그걸 어떻게 찾았는지.
6. `## 검증` — 결정이 의도대로 동작한다는 것을 무엇으로 확인했는지(테스트 이름·개수, PR).
7. `## 감수한 것과 다음` — 이 결정의 대가, 그 대가가 커지는 조건, 그때 바꿀 방법.
8. `## 배운 점` — `~다` 체 bullet 2~3개.

### 쓸 때 주의

- "원인"과 "근거"를 섞지 않는다. 테스트 결과는 원인을 증명하는 근거가 아니라 **결정이 맞았다는 검증**이다(6번).
- 선택지·이유·출처는 PR 본문, 리뷰 코멘트, 작업 세션 기록에 있는 것만. 없으면 사용자에게 묻는다.

## 4. 이어서 개발하는 프로젝트 (RePlant)

2026-10-28 사용자 기준: 처음 버전(세미)과 이어서 개발한 것(최종)을 "세미/최종" 제목으로 딱딱하게 나누지 않는다.

- 본문은 처음 버전 기준으로 둔다. `한눈에 보기`의 기간에 "(처음 버전)"을 붙인다.
- 트러블슈팅 다음, 회고 앞에 `## 추가한 기능과 개선한 점`을 둔다. 표 `| 항목 | 처음 버전 | 바꿀 방향(또는 바꾼 점) | 상태 |`로, 상태는 `예정` → 작업 후 PR 링크.
- 회고의 `다음 개선 방향` 목록은 이 표로 옮긴다(같은 내용을 두 번 쓰지 않는다).
- 이어서 개발하며 생긴 트러블슈팅도 같은 박스 목록에 넣는다. 처음 버전과 구분이 필요하면 근거 PR 번호로 알 수 있다.
